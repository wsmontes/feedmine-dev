FeedMine Feed Runtime V2

Technical Architecture Specification v0.1

Base conceitual: Unified Architecture Blueprint v0.4
Natureza deste documento: proposta técnica executável
Status: arquitetura candidata
Escopo: novo Feed Runtime, canonical supply, acquisition/connectors, selection, publication, session, media e contrato com UI
Fora de escopo: plano de migração do código existente e sequência detalhada de implementação

⸻

1. Propósito

Este documento transforma a macroarquitetura do FeedMine Blueprint v0.4 em uma arquitetura de software concreta.

O objetivo não é descrever como adaptar o FeedMine existente.

O objetivo é responder:

Se construíssemos hoje o motor ideal para cumprir o Blueprint 0.4, como ele deveria funcionar internamente?

A solução deve ser:

* local-first;
* offline-first;
* deterministicamente reproduzível;
* altamente concorrente sem possuir estado concorrente descontrolado;
* independente dos protocolos de aquisição;
* capaz de operar com supply heterogênea;
* econômica em CPU, memória, armazenamento, energia e rede;
* compatível com as restrições de execução do iOS;
* adequada para milhões de instalações independentes;
* compacta em código;
* simples de testar;
* difícil de usar incorretamente.

A arquitetura evita deliberadamente frameworks genéricos, plugin systems, global event buses, object graphs complexos e hierarquias de classes.

O runtime é construído principalmente com:

small value types
+
pure functions
+
SQLite
+
a small number of actors
+
Swift structured concurrency
+
explicit state transitions

⸻

2. Decisão arquitetural principal

A implementação será baseada em três mecanismos complementares:

1. Canonical Local Supply
2. Immutable Published Log
3. Reducer-driven FeedSession

Eles resolvem problemas diferentes.

2.1 Canonical Local Supply

Tudo que chega de sistemas externos é traduzido antes de entrar no domínio operacional do FeedMine.

External Systems
      ↓
Connector
      ↓
Translated AcquisitionBatch
      ↓
Admission Transaction
      ↓
Canonical Local Supply

Depois da Admission Boundary:

RSS
ActivityPub
ATProto
Nostr
API
WebSocket
future protocol

deixam de importar para Selection, Publication, Runway e Presentation.

Essas camadas enxergam apenas FeedMine.

⸻

2.2 Immutable Published Log

O feed que o usuário está navegando não é uma query viva.

Ele é uma história publicada.

FeedEdition
    ├── Segment 0
    ├── Segment 1
    ├── Segment 2
    └── Segment N

Cada FeedSegment é append-only.

Cada card publicado congela:

origin identity
exact origin revision
text
attribution
media identity
render contract
actions
publication metadata

Nada upstream modifica silenciosamente um card já publicado.

⸻

2.3 Reducer-driven FeedSession

FeedSession será uma state machine explícita.

Mas não uma grande enum contendo todas as combinações possíveis.

O estado da sessão será representado por pequenos estados ortogonais e uma função de transição pura:

reduce(
    state: FeedSessionState,
    event: FeedSessionEvent
) -> [FeedSessionEffect]

O actor FeedSession apenas:

serializa eventos
→ chama o reducer
→ executa effects
→ recebe resultados
→ produz snapshots

Isso impede FeedSession de virar FeedStore 2.

4. Modelo de execução

A arquitetura não usará actor para tudo.

Actors existirão somente onde há estado efêmero concorrente cuja serialização precisa ser explicitamente controlada.

Baseline:

FeedSession                  actor
AcquisitionCoordinator       actor
PublicationCoordinator       actor
ImageBroker                  actor
RuntimeWriteCoordinator      actor

Opcionalmente:

ResourceGovernor             actor

se os event sources do sistema exigirem coordenação interna.

Todo o restante será preferencialmente:

struct
enum
pure function
repository
database transaction

7. Composition root

Haverá um único local responsável por construir o runtime.

Exemplo conceitual:

struct FeedRuntimeContainer {
    let database: RuntimeDatabase
    let selection: SelectionEngine
    let publication: PublicationCoordinator
    let acquisition: AcquisitionCoordinator
    let media: MediaPreparation
    let imageBroker: ImageBroker
    let interactions: InteractionCoordinator
}

Não haverá service locator.

Não haverá singleton de domínio.

O application bootstrap cria o container e abre sessions a partir dele.

8. Identificadores

IDs usados no hot path devem ser pequenos.

Baseline proposta:

SourceID             UInt64
ProviderID           UInt64
OriginRecordID       Int64
OriginRevisionID     Int64
EditionID            Int64
SegmentID            Int64
PublicationCardID    Int64
AssetVersionID       Int64
ActionID             Int64

Objetos SQLite locais usam preferencialmente INTEGER PRIMARY KEY.

Isso produz:

* índices menores;
* joins mais baratos;
* menos memória;
* menos bytes em snapshots;
* menos overhead que UUID strings.

Identidades externas continuam opacas e separadas.

Quando uma identidade precisa sobreviver entre databases/dispositivos, uma chave de domínio explicitamente apropriada pode usar UUID/ULID.

IDs internos locais não precisam carregar semântica externa.

⸻

9. External identity

External IDs nunca serão usados diretamente como primary key operacional.

O connector produz:

struct ExternalObjectKey: Sendable {
    let bytes: Data
}

Admission calcula também um fingerprint compacto:

objectFingerprint = hash128(
    connectorScope + externalObjectKey
)

O valor completo continua armazenado como evidence.

O fingerprint permite índice pequeno.

Collision handling deve comparar a external key completa antes de tratar duas identities como iguais.

O mesmo padrão pode ser utilizado para versões externas.

⸻

10. Canonical content model

O hot canonical model deve permanecer pequeno.

struct CanonicalContent: Sendable {
    let headline: String?
    let summary: String?
    let bodyText: String?
    let authoredAt: Date?
    let modifiedAt: Date?
    let observedAt: Date
    let language: LanguageCode?
    let primaryLink: URL?
    let searchProjection: String?
}

Nenhum campo existe porque RSS, Nostr ou ATProto possuem aquele campo.

Ele existe apenas se FeedMine precisa compreendê-lo.

11. AcquisitionBatch físico

O Blueprint apresenta arrays paralelos conceitualmente.

A implementação proposta agrupa claims pertencentes à mesma observation.

Isso reduz coordenação e torna invariantes locais.

struct AcquisitionBatch: Sendable {
    let target: TargetStamp
    let observations: [TranslatedObservation]
    let checkpoint: ConnectorCheckpoint?
}
struct TranslatedObservation: Sendable {
    let externalObject: ExternalObjectKey
    let revision: RevisionDescriptor
    let precedence: RevisionPrecedence
    let content: CanonicalContent
    let provider: ProviderClaim?
    let memberships: [MembershipClaim]
    let relations: [RelationClaim]
    let media: [MediaCandidate]
    let interactions: [InteractionOffer]
    let evidence: ConnectorEvidence?
}

O connector entrega um objeto semanticamente completo.

Ele não entrega rows SQLite.

Ele não persiste.

12. Connector contract

Contrato público:

protocol FeedConnector: Sendable {
    func acquire(
        target: AcquisitionTarget,
        checkpoint: ConnectorCheckpoint?,
        purpose: AcquisitionPurpose
    ) -> AsyncThrowingStream<AcquisitionBatch>
}

O connector possui:

protocol semantics
network semantics
external identity rules
external revision rules
pagination
stream semantics
reconnect semantics
checkpoint interpretation
translation

O runtime possui:

when work should execute
whether the result is still valid
what may be persisted
budgets
target lifetime
supply demand

13. Connector dispatch

Não haverá Universal Connector Registry.

Haverá apenas um resolver compile-time.

Exemplo:

struct ConnectorTable {
    let syndication: any FeedConnector
    func connector(
        for kind: ConnectorKind
    ) -> any FeedConnector {
        switch kind {
        case .syndication:
            syndication
        }
    }
}

Quando o segundo ecossistema existir, adiciona-se explicitamente outro connector.

Essa pequena switch pertence exclusivamente à camada Acquisition.

Nenhum downstream sabe que ela existe.

⸻

14. AcquisitionTarget

AcquisitionTarget representa trabalho operacional.

struct AcquisitionTarget: Sendable {
    let id: AcquisitionTargetID
    let connectorKind: ConnectorKind
    let generation: UInt64
    let configuration: ConnectorTargetConfiguration
}

configuration é connector-owned.

Selection não a lê.

Publication não a lê.

Presentation não a lê.

15. Target leases

Para permitir sharing de work, o planner não solicita simplesmente “start target”.

Ele cria demanda.

struct AcquisitionDemand {
    let purpose: AcquisitionPurpose
    let deficit: SupplyDeficit
    let priority: DemandPriority
}

O planner resolve isso em leases:

Demand A ─┐
Demand B ─┼── Target T
Demand C ─┘

Enquanto pelo menos uma lease válida existir, T pode permanecer ativo.

Isso permite:

200 Sources
→ 25 logical filters
→ 3 connections

sem 200 network tasks.

⸻

16. AcquisitionCoordinator

O actor mantém somente coordenação efêmera:

actor AcquisitionCoordinator {
    var active: [AcquisitionTargetID: ActiveTarget]
}

ActiveTarget contém:

Task
target generation
lease count
purpose/priority
start time

Ele não mantém o conteúdo adquirido.

Ele não é source of truth.

Crash/restart reconstrói esse estado de SQLite + demanda atual.

⸻

17. Streaming e finite acquisition

A mesma interface suporta os dois.

Finite:

start
→ batch
→ finish

Streaming:

start
→ batch
→ batch
→ batch
→ cancellation

Backfill + live:

backfill batches
→ checkpoint transition
→ live batches

Nenhum desses formatos exige branch em Selection ou FeedSession.

⸻

18. Network scheduler

Escalar para milhões de celulares não cria um servidor FeedMine central.

Cria outro problema:

milhões de clientes independentes não podem atacar os mesmos hosts simultaneamente.

O Acquisition Coordinator terá scheduling host-aware.

Cada host possui:

token bucket
concurrency limit
failure/backoff state
next eligible operation

Baseline normal:

global active acquisition targets    4
per-host HTTP operations             2
media transfers                      2

Os números são tuning, não contratos.

⸻

19. Jitter obrigatório

Cadências periódicas nunca serão sincronizadas apenas pelo relógio.

Cada target obtém jitter estável:

jitter = H(
    localInstallationSalt,
    targetID,
    cadenceBucket
)

Isso evita que milhões de instalações executem:

09:00:00 fetch
09:00:00 fetch
09:00:00 fetch
...

O installation salt permanece local.

Não identifica o usuário remotamente.

⸻

20. HTTP efficiency

No Syndication Connector:

ETag
Last-Modified
conditional GET
redirect caching
connection reuse
compression
exponential backoff
full jitter

fazem parte da implementação baseline.

Uma resposta 304 Not Modified deve ser tratada como operação barata.

Network failures afetam cadence.

Não afetam editorial quality.

21. AdmissionEngine

Admission não será actor.

Será uma operação transacional.

struct AdmissionEngine {
    func admit(
        _ batch: AcquisitionBatch,
        in db: Database
    ) throws -> AdmissionResult
}

Cada batch relevante entra em uma transaction SQLite única.

⸻

22. Admission transaction

Fluxo:

BEGIN IMMEDIATE
1. read AcquisitionTarget
2. verify target exists
3. verify generation
4. verify binding state
5. verify WriteAdmissionPolicy
for each observation:
    6. resolve OriginRecord identity
    7. insert record if new
    8. resolve immutable revision
    9. insert revision if new
   10. apply connector precedence
   11. CAS currentRevisionID
   12. upsert memberships
   13. upsert provider attribution
   14. upsert relations
   15. upsert media candidates
   16. upsert interaction offers
   17. store bounded connector evidence
18. persist checkpoint
19. increment SupplyGeneration
COMMIT

Checkpoint nunca é avançado fora desta transaction quando representa aquele conteúdo.

⸻

23. SupplyGeneration

runtime.sqlite possuirá um contador monotônico:

SupplyGeneration

Toda transaction que modifica canonical selectable supply incrementa esse número uma vez.

Isso permite invalidar caches baratos:

CachedRunwayEstimate(
    context,
    supplyGeneration
)

Sem observar dezenas de tabelas individualmente.

SupplyGeneration não possui significado editorial.

É apenas invalidação técnica.

28. Current revision

origin_record.current_revision_id é future-facing.

Atualização será compare-and-swap quando a precedence semantic exigir.

Exemplo:

expected current = V7
incoming V8
CAS V7 → V8

Se outro batch já moveu para V9:

CAS fails

e a precedence rule decide o tratamento.

Não existe “último write ganha” universal.

⸻

29. Selection hot path

Selection não deve reconstruir o canonical graph inteiro para cada Segment.

Será mantida uma read projection estreita.

Proposta:

selection_supply

Campos quentes:

origin_record_id
current_revision_id
provider_id
sort_timestamp
language
availability
media_state
quality_features
search_rowid

Essa projection é atualizada dentro da mesma admission transaction quando necessário.

Ela não substitui as canonical tables.

É um índice operacional reconstruível.

⸻

30. Por que uma read projection

Sem ela, a query típica poderia exigir:

OriginRecord
JOIN current Revision
JOIN Provider
JOIN Media
JOIN Membership
JOIN exposure history
JOIN cluster
...

para centenas de candidatos.

A hot projection permite:

cheap eligibility query
→ bounded candidate set
→ scoring/sequencing in memory

Isso simplifica tanto SQL quanto código.

⸻

31. FeedPlan será data-driven

Não criaremos uma classe para cada tipo de feed.

ResolvedFeedPlan será predominantemente configuration.

struct ResolvedFeedPlan {
    let candidateSpec: CandidateSpec
    let eligibility: EligibilityPolicy
    let scoring: ScoringPolicy
    let sequencing: SequencingPolicy
    let exposure: ExposurePolicy
    let acquisition: AcquisitionPolicy
}

Policies são structs/enums sempre que possível.

Não protocols com dezenas de conformances.

⸻

32. Candidate retrieval

Selection ocorre em duas fases.

Fase 1 — SQLite

Aplica:

hard eligibility
context membership
availability
history exclusions
date bounds
language/region constraints
basic ranking

e retorna um bounded candidate pool.

Fase 2 — memória

Aplica:

scoring
provider diversity
cluster diversity
balance penalties
deterministic sequencing
progressive relaxation

Isso reduz complexidade do SQL e mantém a lógica editorial testável.

⸻

33. Candidate pool

Valores iniciais propostos:

segment target           24 cards
candidate oversampling   4×
candidate pool           ~96 cards

Não são invariantes.

São FeedRuntimeConfiguration.

Mesmo 150–200 candidatos são baratos em um aparelho moderno.

O importante é nunca selecionar sobre milhares de objetos em memória durante scroll.

⸻

34. Scoring

Scoring produz um valor base.

Exemplo conceitual:

quality
+ explicit-context relevance
+ freshness
+ explicit editorial weights

Não exige behavioral personalization.

O runtime não precisa construir perfil de usuário oculto.

⸻

35. Sequencing algorithm

Não será usado um constraint solver complexo.

Baseline: greedy deterministic sequencer.

Para cada posição:

effectiveScore =
    baseScore
  - providerPenalty
  - clusterPenalty
  - balancePenalty

Seleciona-se o maior candidato ainda elegível.

Se nenhum atende ao nível atual:

relax media/category
→ relax provider window
→ allow limited provider repetition

Hard eligibility nunca relaxa.

Complexidade:

O(segmentSize × candidatePool)

Com:

24 × 96

isso é irrelevante computacionalmente.

⸻

36. Determinismo

Toda ordenação termina em tie-break estável.

Exemplo:

effectiveScore DESC
authoredSortDate DESC
stableOriginID ASC

Quando houver variação editorial deliberada:

EditionSeed
SegmentSeed

entram no tie-break deterministicamente.

Uma mesma entrada + mesmo seed + mesmas policies deve gerar a mesma sequência.

⸻

41. Single-flight

O coordinator mantém:

inFlight[EditionID]

Se três solicitações simultâneas pedirem novo supply:

A ─┐
B ─┼→ same publication task
C ─┘

Não são executadas três Selections equivalentes.

⸻

42. Long work fora do actor

O actor não ficará ocupado durante queries/media preparation.

Fluxo:

actor:
    establish single-flight
    capture PublicationToken
outside isolated state:
    selection
    media preparation
    payload construction
transaction:
    re-read tail
    validate token
    validate revision
    validate expected ordinal
    commit
actor:
    finish single-flight

Assim o actor protege coordenação, não vira fila de CPU.

⸻

43. Publication transaction

Transaction final:

BEGIN
read edition
verify EditorialRevision
verify PublicationToken
read current tail
verify expected segment ordinal
remove candidates already published
verify exact revisions
insert FeedSegment
insert PublishedCards
COMMIT

Constraints:

UNIQUE(edition_id, segment_ordinal)
UNIQUE(edition_id, absolute_ordinal)
UNIQUE(edition_id, publication_card_id)

Se o tail mudou:

abort composition
recompose

Nunca encaixar resultado antigo.

52. FeedSession actor

O actor será fino.

Pseudocódigo:

actor FeedSession {

    func handle(_ event: FeedSessionEvent) async {

            state: &state,
            event: event

        for effect in effects {
            execute(effect)
        }
    }
}

O objetivo é que FeedSession.swift permaneça pequeno.

A lógica de transição fica no reducer.

A lógica operacional fica nos services.

I-02 Renderer never initiates network.

113. Decisão final proposta

A implementação técnica candidata é, portanto:

um runtime data-oriented e SQLite-backed, com canonical admission transacional, immutable publication log, Session orientada por reducer, poucos actors de coordenação e Connectors isolados em compile-time boundaries.

Não proponho uma grande graph architecture.

Não proponho um engine baseado em centenas de objetos residentes.

Não proponho uma framework abstrata de protocolos.

Não proponho uma state machine monolítica.

A inteligência está principalmente em:

correct boundaries
small stable identities
immutable facts
bounded working sets
deterministic transitions
transactional admission
cheap local projections
aggressive separation of hot and cold data

Essa combinação é pequena o suficiente para continuar compreensível e forte o suficiente para suportar um FeedMine muito maior que o produto atual.
