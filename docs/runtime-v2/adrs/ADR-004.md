# ADR-004 — Durability, Retention and Dependency Graph

**Status:** Proposed — freeze pending sign-off (Gate 0 not complete).

**Approval:** sign-off happens outside this ADR; plan §1 and the §19 preamble state that the ADR decisions are `proposta para o freeze` and that the revision did not authorize implementing the migration. Every decision below is a proposal awaiting that sign-off, and nothing here constitutes Gate 0 evidence.

**Owns plan rows:** §19 #20 (shared with ADR-001), #21 (shared with ADR-001), #32 (shared with ADR-006), #33. **Evidence PRs:** PR-03, PR-04, PR-06, PR-08, PR-16 (plan §14).

**Normative references:** Blueprint v0.4 §66–§74, §72, §73, §83, §107, §113, §122 rows 20/21/32/33; Technical Architecture v0.1 §24, §26–§28, §64–§66, §77, §83–§85, §98, §105, invariant **I-16**.

## Context

FeedMine currently persists durable state across three unrelated files with three different lifecycles, and no ADR-level rule about which one is authoritative for what. `user.sqlite` lives in `Application Support/Feedmine/` and is documented as the owner of user-owned rows (`feedmine/Services/UserStateStore.swift:16-24`), while bookmark identity lives there and content is hydrated from a different database (`feedmine/Services/BookmarkStore.swift:5-11`, `:114-135`), which already forced an ad-hoc mirror of bookmark pins into the content database so saved articles stay hydratable (`feedmine/Services/BookmarkStore.swift:191-235`). The content database is a **different** file in a **different** directory — `feedmine.sqlite` in Documents (`feedmine/Services/FeedStore.swift:1344-1345`) — yet it is the only place where read/click/consumed history exists: `is_read`, `opened_at`, `clicked_at`, `consumed_at` were added by migrations (`feedmine/Services/FeedStore.swift:7779-7803`) and are loaded back at startup (`feedmine/Services/FeedStore.swift:6144-6166`); retention already deletes those very rows with declared windows and pins in SQL (`feedmine/Services/FeedStore.swift:7203-7235`, `:7241-7284`, `:7297-7327`). The catalog proves a third lifecycle: it is compiled into a temporary file and swapped in with `replaceItemAt` (`feedmine/FeedEngine/SQLiteCatalogStore.swift:63-76`), so it can never host durable runtime tables. Finally, nothing in the app sets a file-protection class or a backup exclusion, so backup policy is currently implicit; plan §6 requires it to be explicit and WAL-aware. Without a decision, V2 would either duplicate user authority or silently orphan bookmarks, read state and published media on the first rebuild or rollback.

## Decision

**D1 — Authority per database.** Each persistent fact has exactly one authority, and no fact has two writers.

| database/file | authority | owner type | rebuild behaviour | on rollback |
|---|---|---|---|---|
| `user.sqlite` (`Application Support/Feedmine/`) | bookmarks, bookmark lists, collections, smart feeds, curated feeds, imported sources, persisted searches, durable read/click/consumed history, durable aliases, bookmark snapshots, cross-database action intents | `UserStateStore` + `UserStateBridge` (existing store stays) | never rebuilt; additive migrations only; a rebuild of any runtime database must leave it byte-identical | untouched; V2 writes must remain readable by the legacy reader (adapter or reader update) |
| `runtime-v2.sqlite` (`Application Support/Feedmine/RuntimeV2/`) | canonical supply (`origin_record`/`origin_revision`), identity mappings, acquisition targets/checkpoints/batches, editions/segments/`published_card`/`published_asset_ref`, asset versions and GC state, exposure facts, session checkpoints | `FeedStorage` (GRDB migrator is schema authority) | fully reconstructible from connectors plus `user.sqlite`; never the source of user identity | left intact, not read by legacy, retained for diagnostics/re-entry; never migrated back into legacy tables |
| `runtime-v2-shadow.sqlite` (`Application Support/Feedmine/RuntimeV2Shadow/`, separate directory) | shadow comparison output only | `ShadowInputBridge` | discardable at any time | discardable |
| `feedmine.sqlite` (`Documents/`) | legacy content cache and legacy read/click columns | legacy `FeedStore` | recomputed by fetching; not durable authority after cutover | required while the rollback window is open: V2 must not delete or rewrite rows it does not own |
| `catalog.sqlite` (managed root; temp-compiled then replaced) | editorial catalog facts | `SQLiteCatalogCompiler`/`CatalogUpdateService` | full recompile and atomic replace | unaffected |
| asset files `Assets/ab/cd/<contentHash>` | bytes for a published `AssetVersionID` | `FeedMedia` / `LocalAssetStore` | re-downloadable only when no publication/bookmark pins them; published bytes are pinned | not read by legacy; may be retained or collected |

**D2 — One canonical database name.** The runtime database is `runtime-v2.sqlite` everywhere: file, logs, code identifiers, docs, tests. The Blueprint §67/§69 and Technical Architecture §24 name `runtime.sqlite`; that name is superseded by plan §6 and MUST NOT appear in V2 code or docs. The path is assembled in exactly one place; no other literal contains the filename. The shadow database is a distinct file in a distinct directory so a shadow run can never open the production file.

**D3 — Explicit backup and file-protection policy.** All SQLite handling is WAL-aware: a backup of an open database copies the database together with its `-wal` and `-shm` companions, or is produced by the SQLite backup API / `VACUUM INTO` on a controlled connection. Copying only the `.sqlite` file and calling it a consistent backup is prohibited — the legacy code already learned this class of bug (`feedmine/Services/UserStateStore.swift:62-64`, `:89-99`, `:140-146`). File protection: `completeUntilFirstUserAuthentication` for `user.sqlite`, `runtime-v2.sqlite` and the shadow database, because acquisition and background maintenance run after the first unlock; `.complete` is prohibited because it breaks background work. Backup participation: `user.sqlite` is included in device backup, because it is the only authority for user data and cannot be reconstructed, which overrides the legacy comment's wish to avoid inflating backups (`feedmine/Services/UserStateStore.swift:17-19`); `runtime-v2.sqlite`, the shadow database, the asset store and `catalog.sqlite` are excluded from device backup (`isExcludedFromBackup`) because they are large and reconstructible.

**D4 — Pool, WAL, foreign keys, single logical writer, migrator authority.** `runtime-v2.sqlite` is opened as a GRDB `DatabasePool` with `journal_mode = WAL` and `foreign_keys = ON` on every connection, matching the existing convention (`feedmine/Services/FeedStore.swift:1348-1355`, `feedmine/Services/UserStateStore.swift:186-189`). One logical writer: all domain writes are explicit transactions, and non-critical telemetry/exposure batching is coalesced on top. The GRDB `DatabaseMigrator` is the single schema authority. `runtime_metadata` is derived compatibility metadata (schema name, compatibility window, last purge/manifest revision) and MUST NOT carry an independent migration counter that could disagree with the migrator's `grdb_migrations` table.

**D5 — `origin_revision` is append-only.** Insert only; a semantically relevant change writes a new revision. Availability, current pointer and projections live on `origin_record`/projections, never on the revision. Any SQL `UPDATE` of a revision row aborts, including from test SQL.

**D6 — Cross-database user actions follow intents → projection → applied marker.** Bookmark/read/collection actions write the intent and the authoritative row in `user.sqlite` first, then project into runtime/legacy compatibility, then mark the intent applied; after a crash, pending intents are replayed. Retries use `setBookmarked(true|false)` with a stable `operation_id`; a toggle is prohibited as a retry unit. A failed projection keeps the intent and surfaces pending/failed state; it never reports success.

**D7 — Durable aliases and a minimal bookmark snapshot.** `user.sqlite` gains durable aliases (namespace + complete durable key → runtime local id, with evidence) and, per bookmark, a minimal content snapshot (title, URL, source/authorship, text, and the media needed for the promised offline card). A rebuilt runtime re-resolves aliases or hydrates from the snapshot; integer runtime IDs are never the only reference. Aliases and snapshot tables are additive migrations in the existing migrator (`feedmine/Services/UserStateStore.swift:195-408`), so older binaries that tolerate unknown tables keep working.

**D8 — Retention classes, quotas, GC.** Retention is expressed as limits per class (age / bytes / editions) that run **before** any collection, plus GC by mark/sweep or transactional refcounts with periodic reconciliation. Pins on a retention root block collection unconditionally. Legacy already implements this shape, with limits and pins declared in SQL rather than in a policy table: a 30-day cutoff with a hard 500-row cap per launch, pinning `bookmark_item`, `smart_feed_item` and recently accessed sources (`feedmine/Services/FeedStore.swift:7203-7235`); a 50-newest-per-source cap that likewise excludes bookmarks (`feedmine/Services/FeedStore.swift:7241-7284`); and weekly maintenance over the same 30-day window plus `VACUUM`/`REINDEX` (`feedmine/Services/FeedStore.swift:7297-7327`). Those numbers are the V2 baseline to measure, not values to hard-code.

| retention class | examples | limit knob | never collected |
|---|---|---|---|
| durable user state | `user.sqlite`: bookmark/collection/smart feed/imported source/persisted search rows, read-click history, aliases, snapshots | none — user data is never quota-evicted; the user deletes it | always retained |
| publication | `feed_edition`, `feed_segment`, `published_card` | retained editions per context (`retainedEditionCount`), max age of superseded editions | active edition, checkpointed edition, any edition reachable from a bookmark snapshot |
| published asset bytes | `asset_version` with durability = published | `assetBytes` for pinned bytes | pinned by edition/draft/bookmark/decode session |
| non-published downloads | fetched-but-unpublished media | `assetBytes` (eviction by quota, LRU) | never pinned; never referenced by a publication |
| decoded cache | in-memory/on-disk decoded images (`feedmine/Services/DiskImageCache.swift:8`, `feedmine/Services/ImageCache.swift:504-508`) | byte cap; discardable at any moment | discarded freely — losing it must not change any published identity |
| connector evidence | `connector_evidence` raw/versioned blobs | `connectorEvidenceBytes`, age | referenced by no durable fact; may expire ahead of supply |
| canonical supply | `origin_record`/`origin_revision` | `runtimeDatabaseBytes`, record age, per-source bounds | revisions referenced by a published card that is still retained |
| reconstructible projections | `selection_supply`, FTS, exposure projections | `runtimeDatabaseBytes` | nothing — may be rebuilt from canonical supply |
| diagnostics/shadow | shadow DB, counters, drop logs | `diagnosticBytes`, age window | explicitly pinned diagnostics only |
| WAL/journal | `-wal`, `-shm` | pass-through checkpoint during maintenance | never deleted while a connection is open |

Numeric budgets are not invented here; see the OPEN items.

**D9 — Recovery paths, never a silent empty database.** Corruption: `PRAGMA integrity_check`/`foreign_key_check` failure opens the database read-only, reports a recoverable state, and offers a controlled rebuild into a new file; the damaged file is quarantined, never overwritten in place. Disk full: the commit fails, the previous edition/session state stays usable, GC runs to reclaim, and the user-visible state is "degraded", never "empty feed" with durable state still on disk. A pre-existing database with an unknown/future schema version fails in a controlled way (compatibility mode if available, explicit error otherwise) and is never auto-erased (`feedmine/Services/UserStateStore.swift:26-107` is the existing precedent for refusing the destructive shortcut).

**D10 — Asset reference consistency.** Write to a temporary file, verify digest and byte count, place it at the content-addressed destination, ensure the durability level chosen (fsync where required), and only then create the `published_asset_ref` in the publication transaction. Orphans after a crash are collectable; a committed reference to bytes that were never written is not acceptable. Published media identity (`AssetVersionID` + digest + dimensions + mime + recipe version) survives eviction of decoded and unpublished bytes.

**D11 — Migration testing matrix, and the ban on erase-on-schema-change.** Every migration is exercised over the matrix below, on a real on-disk database (WAL, foreign keys), not on mocks. Erase-on-schema-change is prohibited: neither `eraseDatabaseOnSchemaChange`, nor a delete/recreate of a durable database, nor `DROP`-then-rebuild may be enabled in the app under any build configuration. An unknown future schema fails controlled (D9).

| scenario | must prove |
|---|---|
| empty database | migrations create schema; `PRAGMA integrity_check` = `ok`; `foreign_key_check` = zero rows |
| reopen after migrate | second launch performs no migration and no data change; WAL recovered cleanly |
| supported previous versions | each shipped version's database migrates forward; no user row loss |
| representative legacy data | bookmark-heavy, read/click-heavy and imported-source-heavy synthetic datasets survive; aliases and snapshots resolve every bookmark |
| interrupted migration | process killed mid-migration either rolls back to the previous version or resumes; never a half-applied marked-as-done state |

**D12 — Compatibility window and rollback proof.** Rollback support is bounded by an explicit window: the supported legacy binaries are enumerated and recorded; rollback must prove V2-full → legacy after relaunch with bookmarks, collections and read state preserved, required content hydratable through the alias/snapshot path, and no double acquisition. The V2 database stays intact during rollback. Flags/bridges are removed only after that window closes (PR-17).

## Rejected alternatives

- **Copy only the `.sqlite` file as a backup.** Rejected: with WAL the committed tail lives in `-wal`; the copy can lose recent commits, and the legacy migration code already documents that size/`-wal` heuristics are unusable (`feedmine/Services/UserStateStore.swift:140-146`).
- **Erase and recreate on schema mismatch (`eraseDatabaseOnSchemaChange`).** Rejected: it silently destroys durable user state; plan §6 forbids it and the interruptible-migration precedent refuses it explicitly (`feedmine/Services/UserStateStore.swift:37-40`).
- **Make `runtime-v2.sqlite` the authority for bookmarks during coexistence.** Rejected: `user.sqlite` is the existing authority and integer runtime IDs change on rebuild (plan §5.2; `feedmine/Services/BookmarkStore.swift:5-11`); a single-authority rule keeps the legacy reader working with no dual-write ambiguity.
- **`runtime_metadata.version` as an independent migration counter.** Rejected: two counters can disagree after a partial upgrade; the GRDB migrator stays the only schema authority and metadata stays derived.
- **`ON DELETE CASCADE` from `origin_record` to publication, or from `origin_revision` to bookmarks.** Rejected: Blueprint §107 forbids `OriginRecord eviction → PublishedCard deletion` and `OriginRevision eviction → Bookmark deletion`; published cards must survive authorised purge of canonical revisions.
- **Unbounded retention ("keep everything, GC later").** Rejected: Technical Architecture §83/§84 require bounded canonical supply and eviction by durability class; unbounded growth is not a design.

OPEN items:

- `OPEN:` exact numeric budgets (`runtimeDatabaseBytes`, `assetBytes`, `connectorEvidenceBytes`, `max_age_seconds`, `max_editions`). Must be fixed by measurement, not by guess — ADR-004 closes them with PR-16 measurements (plan §16); until then the limits exist as knobs with no default.
- `OPEN:` the retained-edition count and which edition is the "checkpointed edition" root. ADR-001 owns that tie-break; ADR-004 owns that the root exists and blocks collection.
- `CLOSED (PR-12)` whether the shadow database is one file per shadow run or one file per mode. **One per installation, not per run**: `RuntimeCompositionRoot.shadowDirectory(applicationSupportDirectory:)` resolves a single fixed `shadow/` directory under Application Support, described in the same file as "beside the runtime's production one and never the same" (`feedmine/RuntimeV2/RuntimeCompositionRoot.swift:8,25,86-93`), and every composition that runs a shadow opens the runtime database in that directory. The consequence for retention is that the shadow's bytes are a stable, bounded diagnostic class — pinned diagnostics, age window (D8) — rather than accumulating one database per launch.
- `CLOSED (PR-08)` the concrete durability level (fsync vs `synchronous = NORMAL`) per asset write. **fsync the file and then its parent directory by default**, selectable down to file-only: `LocalAssetStore.Durability` names both levels and documents why the order matters ("referencing bytes that were never durably written … is not reachable through this path"), and the store's initialiser defaults to `.fileAndDirectory` (`Packages/FeedRuntimeV2/Sources/FeedMedia/LocalAssetStore.swift:12-32,59`). The knob remains per write, so a caller may trade power-loss durability for speed, but it must do so explicitly. Power-loss durability itself is still not proven by process kill (plan §15.1) and belongs to PR-16's rehearsal.
- `CLOSED (PR-00)` which legacy binaries constitute the compatibility window of D12. **The shipped build and the release branch that produced it**: validated release artifact tag `ios/1.0-build.17-4df951c4` → commit `4df951c4af4ecd675ad48100bd4b941f1b766421` ("chore(release): bump build to 17"), with `origin/release/1.0` at `321e38ea9229a496a7bee1da1bacbfa72ae00fae` as an ancestor of the base commit (`docs/runtime-v2/baseline.md` §1, which records HEAD as that artifact plus a 19-line documentation-only append). Rollback therefore means reinstalling the build-17 binary over a database written by V2; the window stays open — and flags/bridges stay in place — until PR-17 shows bookmarks, collections and read state surviving that relaunch with required content hydratable through the alias/snapshot path and no double acquisition.

## Invariants

1. Every persistent fact has exactly one authoritative database, and no fact is written by two components — **I-16**.
2. Removing any reconstructible data (connector evidence, non-pinned revisions, projections, decoded cache) leaves every bookmark, published card payload, active edition checkpoint and user-visible read state semantically intact — **I-16**, Blueprint §72.
3. A published card remains readable, with its exact revision identity and values copied into the payload, after that revision is collected — **I-08**.
4. `origin_revision` rows cannot be updated by any SQL path, including a test script; a semantically different value exists only as a new revision — **I-06**.
5. `published_asset_ref` rows always resolve to `asset_version` rows, and a pinned asset is never collected: `SELECT COUNT(*) FROM published_asset_ref r LEFT JOIN asset_version a ON a.id = r.asset_version_id WHERE a.id IS NULL` is always zero.
6. An acquisition checkpoint never advances beyond content that was durably admitted or durably rejected in the same transaction — **I-11**; shared with ADR-006.
7. Work executed under a stale target generation/binding/lease mutates no membership, no canonical row, no projection and no checkpoint; it may persist only as an orphan cache entry or a bounded diagnostic — **I-12**; shared with ADR-006.
8. The database filename appearing in code, tests and docs is exactly `runtime-v2.sqlite`; no other spelling of the runtime file exists.
9. No build configuration enables erase-on-schema-change, and no code path deletes a durable database to resolve a schema incompatibility.
10. Every backup artifact is WAL-consistent: restoring it yields `PRAGMA integrity_check` = `ok` and the committed rows present at backup time.
11. A bookmark is resolvable after a runtime rebuild and after legacy content deletion, through a durable alias or a bookmark snapshot, without joining a canonical or legacy content row.
12. Cross-database user actions are idempotent under replay: applying the same `operation_id` twice leaves user state unchanged and is reported as a no-op, and no retry unit is a toggle.
13. The runtime database opens read-only (not empty) when corruption, disk-full or an unknown schema is detected while durable state exists.
14. `runtime_metadata` never contradicts the GRDB migrator's applied-migration record.

## Edge cases

- Crash between writing an asset file and committing `published_asset_ref`: the file is an orphan and must be collectable; the reverse order is prohibited (D10).
- Crash between the `user.sqlite` intent write and the runtime projection: replay must find the intent pending and converge; the UI must show pending, not success.
- Disk full during GC, during migration, or during a publication commit: previous edition and all user rows stay valid; GC must not delete the last copy to make room for a write that then fails.
- Backup taken while a connection is open: `-wal`/`-shm` must be included or the checkpoint must be controlled; a size-based heuristic must never decide authority (`feedmine/Services/UserStateStore.swift:37-40`).
- Interrupted migration (existing precedent, `feedmine/Services/UserStateStore.swift:26-107`): both copies must survive until authority is provable; an unverifiable destination must not authorize deleting the other copy.
- Clock skew / wall-clock rollback: age-based retention must use a monotonic or stored watermark plus a wall-clock floor; a backwards clock must not evict fresh rows nor keep expired ones forever.
- Eviction racing an in-flight draft or decode: the pin written by draft/decode must be visible to GC in the same snapshot; a revision needed until publication commit stays protected (plan §6).
- Runtime rebuild changing integer local IDs: aliases and snapshots must re-resolve without reallocating identity by row position.
- Legacy content row deleted while a bookmark still points at it: snapshot hydration must keep the bookmark openable (the current dependency on `feed_item` is exactly this bug, plan §5.2).
- Purge of canonical rows while an edition is active or a bookmark pins it: the active/checkpointed edition and the bookmark root block the purge.
- Deliberate user/privacy purge of published bytes: identity, layout and deterministic fallback survive; the original image is *not* promised after authorised removal (plan §20.2).
- Two modes writing the same user action (legacy + V2 during coexistence): the `user_state_revision` watermark detects drift; projections must re-read rather than assume their prior snapshot.
- Unknown future schema opened by an older build: controlled failure, compatibility mode when available, no auto-erase.
- WAL growth under continuous supply: checkpointing is part of maintenance; a `-wal` larger than budget is a signal to checkpoint, not to delete files.

- `revisionEvictionDoesNotBreakPublishedCard` — a published card whose revision was collected still returns its exact frozen payload — shared with ADR-001, layer `FeedStorageTests/PublicationTests`.
- `decodedEvictionPreservesExactPublishedAsset` — evicting decoded and unpublished caches leaves the published asset identity and bytes resolvable, and the same bytes are re-served without re-identifying them — shared with ADR-001, layer `FeedMediaTests` + `FeedStorageTests`.
- `staleWorkCannotUpdateMembershipOrCheckpoint` — a batch/stream under a stale generation or lease changes no membership, canonical row, projection or checkpoint and leaves at most an orphan cache entry or bounded diagnostic — shared with ADR-006, layer `FeedStorageTests/AdmissionTests`.
- `checkpointNeverAdvancesPastCommittedProgress` — killing the process before, during and after the admission transaction leaves the checkpoint at or behind durably admitted/rejected content — shared with ADR-006, layer `FeedStorageTests/CheckpointTests`.
- `runtimeDatabaseUsesSingleCanonicalName` — the only runtime database filename constructed anywhere in V2 code/tests is `runtime-v2.sqlite`, and the shadow database never resolves to the production path — layer `FeedStorageTests` + boundary scan.
- `walAwareBackupRestoresConsistentDatabase` — a backup taken from a live WAL connection restores with `integrity_check` = `ok` and retains committed rows; a `.sqlite`-only copy demonstrably fails this test — layer `FeedStorageTests/MigrationTests`.
- `interruptedMigrationResumesWithoutDataLoss` — killing the process mid-migration leaves either the previous version or a resumeable partial state, never a half-applied state marked done — layer `FeedStorageTests/MigrationTests` + `feedmineTests`.
- `schemaChangeNeverErasesDurableState` — with a mismatched schema and durable rows present, the database is never deleted or emptied; the failure is controlled — layer `FeedStorageTests/MigrationTests`.
- `unknownFutureSchemaFailsControlled` — opening a database written by a newer schema version fails explicitly (or enters compatibility mode) and preserves all rows — layer `FeedStorageTests/MigrationTests`.
- `diskFullPreservesPreviousEditionAndBookmarks` — an injected write failure during publication and during GC leaves the previous edition usable and every user row intact — layer `FeedStorageTests/RetentionTests`.
- `gcNeverCollectsPinnedAsset` — no GC mode collects an asset pinned by an edition, draft, bookmark, decode session or diagnostic pin — layer `FeedStorageTests/RetentionTests`.
- `retentionEvictsOldestUnpinnedBeforePinned` — under a byte/age budget, unpinned classes are collected first and pinned roots are untouched — layer `FeedStorageTests/RetentionTests`.
- `crossDatabaseActionReplayIsIdempotent` — replaying a `set_bookmarked(true/false)` intent with the same `operation_id` after a simulated crash converges to the requested state and never inverts it — layer `feedmineTests/RuntimeV2UserStateBridgeTests`.
- `rebuiltRuntimeRehydratesBookmarksFromDurableAlias` — after deleting and rebuilding `runtime-v2.sqlite`, every bookmark resolves through aliases or snapshots — layer `feedmineTests/RuntimeV2UserStateBridgeTests`.
- `bookmarkSnapshotHydratesWithoutCanonicalRows` — a bookmark whose legacy `feed_item` row and canonical revision are gone still opens from the snapshot, offline — layer `feedmineTests/RuntimeV2UserStateBridgeTests` + UI check.
- `rollbackPreservesBookmarksCollectionsAndReadState` — V2-full → legacy after relaunch keeps bookmarks, collections and read state, hydrates required content, and performs no double acquisition — layer upgrade/rollback suite (PR-16).
