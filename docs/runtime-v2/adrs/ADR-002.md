# ADR-002 — Context and Revision Model

**Status:** Proposed — freeze pending sign-off (Gate 0 not complete).
Approval of this decision happens outside this ADR, in the freeze review described by
`docs/superpowers/plans/2026-09-17-feedmine-runtime-v2-revised.md` §1 and §19 preamble; until that review
closes, nothing here authorises code. All types, tables, invariants and test names below are proposals.

Scope: which changes invalidate selection, publication and render; the identity of an intent versus the
fingerprint of its editorial inputs; the editorial clock; editorial preferences; catalog revisions; user-state
revisions; warm-restore validity; edition replacement boundaries.

## Context

The V2 runtime must answer "was this history produced under the same rules?" without reading global mutable
state, and must restore a locally published edition without touching network, Selection or the catalog
(plan §8, §9, §16; Blueprint §17, §18, §96, §99). The repository already contains the failure mode this ADR
must not repeat: `feedmine/Services/FeedStore.swift:658-674` builds `pageCacheSignature` — the closest existing
analogue of an editorial fingerprint — by concatenating fields from live singletons (`ContentFilterStore.shared`,
`activePreset`, `activeMood`, taxonomy URLs, languages) with a `\u{1F}` separator, so the fingerprint is neither a
snapshot of values nor a bounded field encoding. `feedmine/Services/FeedDisplayState.swift:519-524` then folds the
render-materialization decision (`id|layout|hasMedia` in `pageFingerprint`) into the same freshness concept,
which Blueprint §17 and §19 explicitly separate: `EditorialRevision` describes the rules that produced the
history, `RenderEnvironmentRevision` describes only visual materialisation. Restoration today has no validity
contract at all: `feedmine/Services/FeedDisplayState.swift:571-577` decodes the cached page with `try?` and accepts
it whenever `items` is non-empty — no schema version, no integrity check, no context compatibility, while
`feedmine/Services/TaxonomyStore.swift:65,648-655` shows the stronger precedent the runtime should follow
(`cacheSchemaVersion` + count + fingerprint rejection). Finally, existing revisions are volatile counters read by
consumers but never captured as values: `feedmine/Services/SourceRegistry.swift:82-83`
(`sourceRevision`, `enablementRevision`), `feedmine/Services/FeedDisplayState.swift:60` (`readStateRevision`), and
the catalog's own `revision` in `feedmine/Services/CatalogUpdateService.swift:53-54`, whose
`supportedSchemaVersion` rejection at `:97-99` is the model for controlled schema refusal.

## Decision

**D1 — `ContextKey` is the identity of an intent, not a fingerprint of inputs.**
A `ContextKey` identifies *which feed the user asked for* (main, source, collection, bookmarks, search, smart feed)
plus a durable scope key. It never changes because editorial inputs changed; it changes only when the intent
changes. It never contains autoincrement row ids (plan §5.1) and never contains a digest of inputs.

**D2 — `EditorialRevision` is the versioned fingerprint of the *effective* editorial inputs.**
`EditorialRevision` is the value `(schemeVersion: Int, digest: String)` where `digest` is the lowercase hex
SHA-256 of the canonical serialization of `EditorialInputs` (D3, D4). It is not a counter, not a row id and not a
hash of upstream payloads. Two revisions are equal iff their scheme versions are equal and their digests are
equal; digest comparison across different scheme versions is prohibited (D5).

**D3 — Canonical serialization rules (normative).**
The serialized form is UTF-8 and consists of explicit, ordered fields; each field is emitted as
`name` `=` `typeTag` `:` `len` `:` `bytes` with a single `\n` terminator, where `len` is the byte count. Arrays are
emitted in the order defined in D4 and are never emitted from `Set`/`Dictionary` iteration order. Integers are
decimal ASCII; timestamps are integer milliseconds since the Unix epoch; numbers and booleans never use
locale-dependent formatting. `Swift.Hasher`, `hashValue`, `ObjectIdentifier`, `String.hashValue`, `Date`'s
`description`, `Locale.current` and `TimeZone.current` MUST NOT appear anywhere in fingerprint production; a
persisted fingerprint must be recomputable in a different process and a different launch. This matches the
existing, deliberate precedent in `feedmine/Services/FeedDisplayState.swift:427-437` (SHA-256 "not `hashValue`:
Swift seeds `hashValue` per process") and `feedmine/Services/ImageCache.swift:713-716` (FNV-1a "deterministic
across launches, unlike String.hashValue").

**D4 — Canonical field order and the exclusion list.**
`EditorialInputs` serializes exactly these fields, in this order: `revisionSchemeVersion`, `planIdentity`,
`planSchemaVersion`, `policies[]` (ordered `policyID` + `policyVersion` pairs), `algorithmVersion`,
`sourceSelection[]` (sorted `sourceKey` + `enabled`), `presetIdentity`, `region`, `contentType`, `languages[]`
(sorted), `mood`, `contentFilters[]` (sorted `filterID` + resolved keywords, sorted), `taxonomyURLs[]` (sorted),
`relevantCatalogDigest`, `relevantUserStateDigest`, `exclusionPolicyVersion`, `editorialClockBucket`,
`selectionSchemaVersion`.
Explicitly excluded, and therefore forbidden to enter the digest: edition/segment seed (per-edition randomness,
not an input — Blueprint §58, Technical Architecture §36); `catalogGeneration` and `userStateRevision` as raw
counters (only their *relevant projections* are inputs — D6); connector identity, connector implementation and
target checkpoint (Blueprint §17: "connector/target checkpoint não é `EditorialRevision` por si só"); binding and
endpoint; connector evidence and raw payloads; asset bytes, media preparation state and eviction state; window,
viewport, scroll anchor and exposure facts; the whole of `RenderEnvironmentRevision`; any per-process hash.

**D5 — Fingerprint versioning rule.**
`EditorialRevisionSchemeVersion` starts at `1` and is itself a serialized field. Any change to the field set,
the field order, an encoding, the separator grammar, or the digest algorithm MUST bump it. A build that reads a
`schemeVersion` it does not support MUST NOT compare digests against it: it records the edition as
`revisionNotComparable`, keeps it displayable while `PublicationSchemaVersion` is supported (D9), refuses to
reuse it as the base of a new draft, and requires an explicit refresh before any editorial comparison. Digest
strings are never migrated, truncated, reinterpreted or reused across schemes. Old revision rows are retained
according to ADR-004.

**D6 — Relevance qualifiers: catalog generations and user-state revisions are separate authorities.**
`CatalogGeneration` is the catalog's monotone authority counter (catalog `revision` today:
`feedmine/Services/CatalogUpdateService.swift:53-54`) and `UserStateRevision` is the durable user-state
watermark (`readStateRevision` today: `feedmine/Services/FeedDisplayState.swift:60`). Neither is an
`EditorialRevision` input by itself. What enters the digest is `relevantCatalogDigest` and
`relevantUserStateDigest`: the digests of exactly the projection the resolved plan reads (source membership and
enablement for eligibility; read/bookmark/consumed/clicked keys for plans whose eligibility reads them). A
catalog rebuild that leaves the relevant projection unchanged therefore changes `CatalogGeneration` but not
`EditorialRevision`; a bookmark toggled on a card that no plan reads for eligibility changes
`UserStateRevision` but not `EditorialRevision`. Authority for both counters is ADR-004; `HistoryScope` and which
user-state keys a plan may read are ADR-007.

**D7 — `RenderEnvironmentRevision` changes materialisation, never editorial history.**
It is `(layoutWidthClass, dynamicTypeSize, localeIdentifier, textDirection, displayScale)` in canonical order. It
is carried in the session and in `SessionStamp`; it is never an input of D4 and never part of an edition's
identity. A change re-materialises the same `PublicationCardID`s and must not re-run Selection. Locale enters the
editorial digest only through the *resolved* content-filter keyword set (D4) and the resolved language selection,
because `feedmine/Models/ContentFilter.swift:34-45` resolves keywords under `Locale.current` and
`feedmine/Services/FeedStore.swift:832-836` reads the device language for the filter pass today: those are
editorial inputs, but they must be captured as values in the token, never read implicitly during evaluation.

**D8 — Warm restore validity: supported schema + intact payload + compatible context; no network.**
An edition is warm-restorable for a `ContextKey` when (R1) its stored `context_key` equals the requested key,
(R2) its `publication_schema_version` is in the build's supported set, and (R3) every restored segment's payload
recomputes to its stored `payload_digest` and decodes. A schema *newer* than the build is a controlled refusal,
never a permissive interpretation (plan §19 additional decisions; `CatalogUpdateService.swift:97-99` is the
precedent). Restoration MUST perform zero network calls, zero Selection and zero catalog refresh (plan §16,
Blueprint §96). The following are NOT restore conditions and must not block a warm paint: a different (newer)
`EditorialRevision` — the edition stays displayable and a successor is scheduled at the next explicit boundary
(D9); a different `RenderEnvironmentRevision` in either direction (D7); a different `CatalogGeneration` or
`UserStateRevision`; evicted asset bytes (ADR-001/ADR-004 own the placeholder policy). When no edition satisfies
R1–R3 the case is classified as cold/recovery and reported as such, not hidden inside the warm-start distribution
(plan §16, §19 #17).

**D9 — Edition replacement is explicit; passive changes never swap the visible edition.**
The active edition for a `ContextKey` is replaced only by an explicit refresh, an explicit context change, or a
lifecycle boundary, following the resolved plan's policy — and only after a successor's first segment is
committed (plan §9; Blueprint §97, §99). Refresh failure keeps the previous edition active. Passive catalog
changes, `SourceBinding` changes, endpoint changes, connector/checkpoint advancement, `CatalogGeneration`
increments, `UserStateRevision` increments and `SupplyGeneration` increments never replace the visible edition by
themselves (plan §9; Blueprint §99). An edition keeps its `EditorialRevision` for the duration of the current
navigation (Blueprint §18/§99).

**D10 — Clock rules.**
The editorial clock is injected (Technical Architecture §102 lists `Clock` as a permitted port) and is read at
draft start only, never at evaluation time. Its canonical contribution to `EditorialRevision` is
`editorialClockBucket`: a policy-defined bucket index derived from the wall clock, with the bucket resolution
owned by the resolved plan's policy version. A bucket rollover makes a new revision *eligible*; it does not abort
an in-flight draft (D11) and does not swap the visible edition (D9). Monotonic time is used for dwell and
exposure intervals only (ADR-007). Backwards wall-clock skew never changes a committed revision or rewrites a
committed edition: the bucket is qualified monotonically against the last persisted reading.

**D11 — Draft starvation rule.**
`SupplyGeneration` is not an editorial input and never invalidates a draft. A draft is invalidated only by (a) a
`ContextKey` or edition/epoch change, (b) a change of the resolved `EditorialRevision` observed at an explicit
boundary, (c) loss of hard eligibility for a pinned revision, or (d) a tail/ordinal conflict at commit (plan §9;
ADR-006 owns the CAS). A draft pins the exact `OriginRevisionID`s, the seed and the revision it was built under;
newly admitted supply is eligible for the *next* draft, and only cards whose hard eligibility changed are
revalidated at commit. This is the explicit answer to the starvation risk of plan §9: under a continuous stream,
the edition still swaps only at the explicit boundaries of D9, so neither the visible history nor the draft queue
oscillates with supply.

**D12 — `ContextKey` and `EditorialRevision` are session-visible, not UI-visible.**
`FeedSessionState` carries `context`, `editorialRevision`, `publicationEpoch`, `publicationToken` and
`renderEnvironment` (Technical Architecture §48); `SessionStamp` carries context, revision and epoch (§51).
Snapshots expose the materialised cards and their monotonic number only; a client never compares revisions
itself, and a stale stamp result is discarded rather than applied (§51).

## Rejected alternatives

- **One uuid/counter per context as the revision.** Rejected: a counter cannot be recomputed after a crash, cannot
  be compared across two databases, and cannot prove that two runs used the same rules (plan §8; Blueprint §58).
- **Hashing with `Swift.Hasher`/`hashValue`.** Rejected: Swift seeds hashing per process, so a persisted
  fingerprint would be unreachable after relaunch. This is measured history, not theory —
  `feedmine/Services/FeedDisplayState.swift:427-437` and `feedmine/Services/ImageCache.swift:713-716`.
- **Putting the render environment into the editorial revision.** Rejected: it would fork editorial history by
  Dynamic Type, device width or locale, contradict Blueprint §17/§19, and break
  `dynamicTypePreservesEditionAndCardIDs` by construction.
- **Letting `CatalogGeneration` or `UserStateRevision` into the digest directly.** Rejected: a catalog rebuild or a
  single read toggle would invalidate every draft and force a new edition — the starvation case of plan §9 and the
  passive-swap case Blueprint §99 forbids.
- **Treating connector implementation or checkpoint advancement as an editorial revision change.** Rejected:
  Blueprint §17 states they do not create a new `EditorialRevision` by themselves; they alter eligibility only
  through the plan-relevant projection (D6).
- **A permissive restore that decodes whatever payload it finds.** Rejected: the current behaviour at
  `feedmine/Services/FeedDisplayState.swift:571-577` (`try?` decode + non-empty check) cannot distinguish an
  intact page from a stale, foreign-context or schema-shifted one, which violates plan §16 and §19 #17.

## Schema and types

```sql
-- Local surrogate ids are never exported across databases (ADR-003/ADR-004 own id rules);
-- the durable identity of a revision is the pair below.
CREATE TABLE editorial_revision (
    revision_id      INTEGER PRIMARY KEY,
    scheme_version   INTEGER NOT NULL CHECK (scheme_version > 0),
    digest           TEXT    NOT NULL CHECK (length(digest) = 64),
    canonical_inputs TEXT    NOT NULL,   -- exact serialized bytes, for audit and replay
    created_at_ms    INTEGER NOT NULL,
    UNIQUE (scheme_version, digest)
);

CREATE TABLE feed_edition (
    edition_id                 INTEGER PRIMARY KEY,
    context_key                TEXT    NOT NULL,     -- canonical ContextKey serialization
    editorial_revision_id      INTEGER NOT NULL REFERENCES editorial_revision(revision_id),
    publication_schema_version INTEGER NOT NULL CHECK (publication_schema_version > 0),
    publication_epoch          INTEGER NOT NULL,
    seed                       BLOB    NOT NULL,
    payload_digest             TEXT    NOT NULL CHECK (length(payload_digest) = 64),
    state                      TEXT    NOT NULL CHECK (state IN ('draft','active','retired','failed')),
    created_at_ms              INTEGER NOT NULL
);

-- One active edition per context (plan §6, "active edition por contexto").
CREATE UNIQUE INDEX ux_feed_edition_active_context
    ON feed_edition (context_key) WHERE state = 'active';

-- Plan-relevant projections only: these are what D6 hashes, not the authorities themselves.
CREATE TABLE editorial_input_watermark (
    context_key             TEXT    NOT NULL PRIMARY KEY,
    catalog_generation      INTEGER NOT NULL,
    user_state_revision     INTEGER NOT NULL,
    relevant_catalog_digest TEXT    NOT NULL CHECK (length(relevant_catalog_digest) = 64),
    relevant_user_digest    TEXT    NOT NULL CHECK (length(relevant_user_digest) = 64)
);

CREATE TABLE session_checkpoint (
    context_key                 TEXT    NOT NULL PRIMARY KEY,
    edition_id                  INTEGER NOT NULL REFERENCES feed_edition(edition_id),
    publication_card_id         INTEGER NOT NULL,
    absolute_ordinal            INTEGER NOT NULL,
    anchor_placement            TEXT    NOT NULL,
    render_environment_revision TEXT    NOT NULL,  -- recorded, never compared for restore (D7, D8)
    updated_at_ms               INTEGER NOT NULL
);
```

```swift
struct ContextKey: Hashable, Sendable, Codable {
    enum Surface: String, Codable, Sendable {
        case main, source, collection, bookmarks, search, smartFeed
    }
    let surface: Surface
    let scopeKey: String          // durable scope key (ADR-003); never an autoincrement row id
    let planIdentity: String      // resolved plan family, not its inputs
}

struct EditorialRevision: Hashable, Sendable, Codable {
    static let currentSchemeVersion = 1
    let schemeVersion: Int
    let digest: String            // lowercase hex SHA-256 of EditorialInputs canonical form
}

/// Serialization order is the declaration order; no field may be added without bumping the scheme (D5).
struct EditorialInputs: Sendable, Equatable {
    let revisionSchemeVersion: Int
    let planIdentity: String
    let planSchemaVersion: Int
    let policies: [PolicyVersion]          // ordered (policyID, policyVersion)
    let algorithmVersion: Int
    let sourceSelection: [SourceSelection] // sorted (sourceKey, enabled)
    let presetIdentity: String
    let region: String
    let contentType: String
    let languages: [String]                // sorted
    let mood: String
    let contentFilters: [ResolvedContentFilter] // sorted (filterID, resolvedKeywords) — locale-resolved
    let taxonomyURLs: [String]             // sorted
    let relevantCatalogDigest: String
    let relevantUserStateDigest: String
    let exclusionPolicyVersion: Int
    let editorialClockBucket: Int64
    let selectionSchemaVersion: Int
}

struct RenderEnvironmentRevision: Hashable, Sendable, Codable {
    let layoutWidthClass: String
    let dynamicTypeSize: String
    let localeIdentifier: String
    let textDirection: String
    let displayScale: Int
}

enum EditionRestoreDecision: Sendable, Equatable {
    case restorable                        // warm: R1–R3 satisfied
    case restorableStaleEditorially        // warm: revision differs, successor at next explicit boundary
    case revisionNotComparable             // warm: unknown EditorialRevision scheme (D5)
    case incompatiblePublicationSchema     // cold/recovery; newer schema is a controlled refusal
    case payloadCorrupt                    // cold/recovery; counted
    case noEdition                         // cold
}
```

`OPEN:` the physical encoding of `ContextKey` for non-`main` surfaces (which `scopeKey` namespaces exist for
source/collection/bookmark/search/smart feed) — ADR-003 must close the namespace list.
`OPEN:` whether `session_checkpoint.render_environment_revision` is stored at all or recomputed from the live
environment on restore — ADR-001 must close it together with the render contract.
`OPEN:` the exact bucket resolution and which policy owns it (per plan or per runtime) — ADR-005 must close it with
the cadence/backoff policy; this ADR only fixes that the bucket is an input and that rollover is not an abort.

## Invariants

1. Identical `EditorialInputs` produce an identical `(schemeVersion, digest)` in a different process and a
   different launch, and the digest never depends on hash seeding. (No I-nn; grounded in
   `FeedDisplayState.swift:427-437`.)
2. A different `EditorialRevision` is produced if and only if at least one D4 field changes for the same
   `ContextKey`; `RenderEnvironmentRevision` never appears among them. (Blueprint §17.)
3. `ContextKey` equality is invariant under every change of D4 and of the render environment: it changes only
   when the surface/scope/plan identity changes. (Blueprint §111.)
4. Two drafts sharing an `EditorialRevision` and a seed over the same supply snapshot produce the same ordered
   `OriginRevisionID` sequence, and the sequence is not affected by new supply admitted during the draft.
   (Blueprint §58; Technical Architecture §36, §104.)
5. A `SupplyGeneration` increment alone never invalidates a draft and never changes the active edition.
   (Plan §9; Technical Architecture §23.)
6. A passive catalog, binding or endpoint change never changes the active edition for any `ContextKey`.
   (Blueprint §99; plan §9.)
7. An `EditorialRevision`/`CatalogGeneration`/`UserStateRevision` change never rewrites a committed segment or a
   committed card payload. (I-09, I-07; ADR-001 owns the payload freeze.)
8. Every card in a committed segment references the exact `OriginRevisionID` pinned in the draft, regardless of
   supply admitted or clock advanced since the draft started. (I-08.)
9. Warm restore under D8 R1–R3 performs zero network calls, reads no catalog and runs no Selection. (I-02.)
10. Restoring a `FeedWindow` under a changed `RenderEnvironmentRevision` preserves the edition's
    `PublicationCardID` set and order; only materialisation differs. (I-13, I-14.)
11. A failed refresh leaves the previous edition in state `active`; there is no committed state in which a
    `ContextKey` that had an active edition has none. (Plan §9; Blueprint §97.)
12. Backwards wall-clock skew never changes a committed `EditorialRevision` and never rewrites a committed
    edition. (No I-nn; D10.)
13. Exposure and dwell are never derived from an `EditorialRevision` change or from a rerender. (I-15.)

## Edge cases

- Crash between the successor's segment commit and the active-edition swap: the old edition must remain the only
  `active` row (partial unique index), and the successor must be recoverable or collectable, never a second
  active edition.
- Crash while writing `canonical_inputs`: the revision row and the edition that references it commit together, or
  neither does.
- Draft outstanding while `CatalogGeneration` advances without changing the relevant projection: the draft
  commits unchanged (D6, D11).
- Draft outstanding while a source is disabled: the pinned revision loses hard eligibility, and revalidation at
  commit must fail that card rather than shrink the segment silently.
- Draft outstanding while the user reads a card that the draft contains: `UserStateRevision` advances; the digest
  changes only for plans that read it; the published payload must not carry the overlay (ADR-001/ADR-007).
- Clock jumps forward across several buckets, or backwards across a timezone/DST boundary: the bucket is
  qualified monotonically; no draft abort, no history rewrite, at most a new revision eligible at the next
  explicit boundary.
- Locale change that alters the resolved content-filter keyword set: the editorial digest changes at the next
  explicit boundary while the *display* locale change alone does not (D7).
- Dynamic Type change during an active scroll: cards re-materialise with the same `PublicationCardID`s and the
  anchor is preserved by the window, not by the digest.
- Restoring an edition written by a build with a newer `PublicationSchemaVersion`: controlled refusal to the
  cold/recovery path; no permissive decode, no silent empty feed.
- Restoring an edition with a valid schema but an unknown `EditorialRevisionSchemeVersion`: warm, displayable,
  `revisionNotComparable`, not reusable as a draft base (D5).
- Restoring a payload whose digest does not recompute (partial write, torn file, foreign-context page copied in):
  reject and count; never paint a mixture of two compositions.
- Two contexts whose `scopeKey` strings collide but whose `Surface` differs (e.g. a collection and a smart feed
  named alike): D1 keeps them distinct; a `scopeKey`-only key would merge two histories.
- Catalog rebuild that reallocates row ids: it must change neither `SourceID` (ADR-003) nor `ContextKey`; a
  `ContextKey` derived from a row position would break restore silently.
- Edition eviction/retention sweep while a session is restoring it: ADR-004 must guarantee the retention root for
  the active edition and for the in-flight restore.

## Named acceptance tests

These were written as proposed criteria. **Checked 2026-09-18: they are proposals no longer** — the criteria are implemented and pinned by real tests, and `contract-matrix.md`'s invariant table with `baseline.md` §8.54 carries the row-by-row binding. Layer names still refer to the package targets in plan §3.

- `editorialPolicyChangeChangesRevision` — changing a policy version in D4 changes `(schemeVersion, digest)` for the
  same context while every other input is held fixed — `FeedDomainTests` (plan §19 #15, PR-05).
- `dynamicTypePreservesEditionAndCardIDs` — a Dynamic Type and width change re-materialises the same edition with
  the same `PublicationCardID` order and does not change `EditorialRevision` — `FeedUIBridgeTests` (plan §19 #16,
  PR-07, 13).
- `passiveCatalogChangeDoesNotSwapVisibleEdition` — activating a different catalog revision and a changed binding
  endpoint leaves the active edition id unchanged until an explicit refresh — `FeedRuntimeTests` (plan §19 #18,
  PR-07, 13).
- `compatibleEditionRestoresWithoutSelection` — with an edition satisfying R1–R3, restore emits a snapshot without
  any Selection run, catalog read or network call — `FeedRuntimeTests` (plan §19 #17, PR-06, 07).
- `failedRefreshKeepsPreviousEditionVisible` — a refresh that fails after the successor draft started leaves the
  previous edition `active` and the session on a recoverable state — `FeedRuntimeTests` (plan §19 #25, PR-06, 07).
- `noSupplyDoesNotLoopOrEraseHistory` — exhausted supply produces an explicit exhausted state, bounded retries and
  a still-navigable committed history, with no duplicate-filled loop and no erased segments — `FeedRuntimeTests`
  (plan §19 #37, PR-09, 13).
- `sameEditorialInputsProduceSameRevisionAcrossProcesses` — the digest recomputed in a fresh process equals the
  persisted one (D3; guards against hash-seeded fingerprints) — `FeedDomainTests`.
- `renderEnvironmentChangeDoesNotChangeEditorialRevision` — D7 exclusion, asserted on both digest and edition id —
  `FeedDomainTests`.
- `clockBucketRolloverDoesNotAbortInFlightDraft` — a bucket crossing during a draft changes the next draft's
  revision but the current draft still commits — `FeedRuntimeTests`.
- `supplyGenerationIncrementKeepsDraftValid` — admission between draft start and commit does not invalidate the
  draft and does not swap the edition (D11) — `FeedRuntimeTests`.
- `irrelevantCatalogRevisionKeepsEditorialRevision` — a `CatalogGeneration` increment whose relevant projection is
  unchanged leaves the digest equal (D6) — `FeedStorageTests`.
- `restoreRejectsUnsupportedPublicationSchemaVersion` — a newer schema produces
  `incompatiblePublicationSchema` and the cold/recovery path, not a decode attempt — `FeedStorageTests`.
- `restoreRejectsTamperedPayload` — a payload whose digest does not recompute produces `payloadCorrupt` and no
  snapshot — `FeedStorageTests`.
- `contextKeySeparatesSurfacesWithEqualScopeKey` — identical `scopeKey` under two surfaces yields two editions and
  two checkpoints — `FeedDomainTests`.
- `staleEditorialRevisionKeepsEditionDisplayableUntilExplicitRefresh` — warm restore with a newer revision paints
  the stored edition and schedules, but does not perform, a successor — `FeedRuntimeTests`.
- `editorialRevisionCarriesResolvedContentFilterKeywords` — the digest changes when the locale or filter
  definition changes the resolved keyword set, and does not change when only the display locale changes —
  `FeedDomainTests`.
