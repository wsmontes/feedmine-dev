# ADR-001 — Publication / Media

**Status:** `Proposed — freeze pending sign-off (Gate 0 not complete)`

Approval of this ADR happens outside this document (migration plan §1 and §19 preamble). Nothing here authorizes implementation; every type, invariant and test name below is a proposal for the freeze.

**Semantic authority:** Blueprint v0.4 §43, §44, §47, §48, §50, §53–§58, §97–§99, §105, §110, §122 (`b230342258566a2366dd07cd64eea5672504e2f7dff3b3b7f3fa7a55a07344e7`).
**Subordinate technical proposal:** Technical Architecture v0.1 §6, §38–§47, §62, §64–§66, §105, §107 I-06…I-10 (`f8484da4da0ff3778728cfc7ba0edba785ceb7ca257ff7ee9c8ab84d86cb29c3`).

## Context

ADR-001 fixes the published log: what a publication freezes, who may append to it, how a successor Edition replaces the visible history, what happens when the upstream mutates, when assets are committed, and what identity survives eviction or deliberate byte removal. The Blueprint answers these at the macro level (Blueprint §57: "`PublicationCoordinator` continua sendo o único produtor de história publicada"; §54 defines `PublishedCardPayload`; §56 keeps `PublicationSchemaVersion` independent; Technical Architecture I-06…I-10 state immutability and single-writer as normative invariants), but the plan leaves the physical contract open until the freeze — including the deliberate adjustments of plan §20.2 (media identity survives eviction; after deliberate byte removal only identity/layout/fallback are guaranteed) and §19 rows #17–#27 and #38.

The repository forces the decision, because its current publication layer is the exact opposite shape:

- `feedmine/Models/FeedItem.swift:393-401` derives `id` as `SHA256("sourceURL|guid_or_link")` with a `source+title+timestamp` fallback — identity lives in the parse path, not in a publication record.
- `feedmine/Models/FeedCardPresentation.swift:67` sets `var id: String { item.id }`; SwiftUI identity is a byte-derived string, while Blueprint §10 and I-14 require `PublicationCardID`.
- `feedmine/Models/FeedCardPresentation.swift:70-81` carries `FeedItem` plus a snapshot `isRead`/`isBookmarked` stamped at preparation; there is no durable published payload and no separate overlay channel (plan §9).
- `feedmine/Services/FeedStore.swift:8274-8287` already documents the freeze intent — a late image resolution deliberately does **not** rewrite the published card, "the very shift the freeze exists to prevent" — but only as a convention inside an 8 293-line file, with no constraint that can enforce it.
- `feedmine/Services/PreparedPageRestoration.swift:12-13,17,43,66-67` bounds decode to 30 rows and restores the rest as `.textOnly` with `media: .none`; this is exactly the "text + deterministic local representation is enough" rule of plan #22, but it is a performance heuristic, not a stated publication guarantee.
- `feedmine/Services/MediaAssetStore.swift:304-312` derives the asset cache key with FNV-1a over `url.absoluteString`; plan §10 rejects the URL as an asset identity because the server can swap bytes at a stable URL.
- `feedmine/Services/MediaAssetStore.swift:18-22` already enforces `12 * 1024 * 1024` compressed bytes, `maxSourceDimension = 12_000` and `maxSourcePixels = 50_000_000`; the plan (§10) makes these the baseline that must not be relaxed by accident.
- `feedmine/Services/FeedStore.swift:7255-7281` retention deletes rows beyond the 50 newest per source (excluding bookmarks); under the current model that deletion is one join away from the visible page (I-16 violation in waiting), whereas `user.sqlite` is the user-state authority (`feedmine/Services/UserStateStore.swift:4-23`) and `BookmarkStore` hydrates content from `feedmine.sqlite` (`feedmine/Services/BookmarkStore.swift:115-120`, `:190-194`).
- `feedmine/Views/FeedScreen.swift:892-896` calls `noteVisibleIndex` and `loadMoreIfNeeded` from `onAppear`; viewport observation is currently causal for acquisition, which the publication contract must not depend on.

## Decision

**D1 — The published log is append-only and single-writer.** `FeedEdition` grows only by appending immutable `FeedSegment`s (Blueprint §57). `PublicationCoordinator` is the only component authorized to write `feed_edition`, `feed_segment`, `published_card` and `published_asset_ref` (Blueprint §57, Technical Architecture §40, I-10). Connectors, Selection, MediaPreparation and the renderer have no write path and no API surface for append.

**D2 — Occurrence identity is `PublicationCardID`.** `PublicationCardID` identifies a published occurrence; `OriginRecordID`/`OriginRevisionID` identify canonical content; the user-state durable key identifies the user's intent (plan §5.1). SwiftUI identity, anchor identity and overlay keys use `PublicationCardID` only (Blueprint §10, I-14). Array position, URL, digest and `FeedItem.id` are never identity.

**D3 — Append requires a token, single-flight, and a tail CAS.** `PublicationCoordinator` keeps `inFlight[EditionID]` (Technical Architecture §41). A `PublicationToken` captures edition, epoch, `EditorialRevision` and the expected tail (segment ordinal + `feed_edition.version`). Long work (Selection, media preparation, payload construction) runs outside the coordinator's isolated state (Technical Architecture §42); the commit transaction re-reads the tail, validates token, eligibility and expected ordinal, then appends. A tail mismatch aborts the composition, releases temporary pins, and recomposes with bounded retry; a stale draft is never renumbered and never "fitted in" (Technical Architecture §43). Uniqueness in SQLite is the invariant; the CAS only turns a lost race into a bounded retry.

**D4 — Publication freezes the payload.** A `PublishedCardPayload` freezes: the chosen attribution/membership (`PublishedOrigin`: `originRecordID`, `originRevisionID`, chosen `sourceID`/`providerID` and their display names — Blueprint §53), text, timestamp with its epistemic kind, the media set, the primary action, the interaction summary, and the `RenderContract` (Blueprint §54). It also freezes edition seed, segment seed, policy/revision identity, the exact `OriginRevisionID` and the exact media version (Blueprint §58). A later catalog or attribution edit does not rewrite it (Blueprint §53).

**D5 — The payload is self-sufficient.** `published_card` carries every value needed to render text, attribution, timestamp, media identity and action, plus the copied revision identity and `PublicationSchemaVersion` (Technical Architecture §44). No mandatory join to `origin_record`/`origin_revision` is permitted at restore, render or window materialization (plan #20). Consequently there is **no foreign key from publication to canonical**, and no `ON DELETE CASCADE` from origin to publication may exist anywhere in the schema (plan §6); canonical eviction or authorized purge must leave published cards intact (I-16, Blueprint §72).

**D6 — Precedence of validity.** An upstream mutation updates future-facing availability/current pointers only; committed segments are unchanged (Blueprint §44, §55, I-09). A passive catalog, `SourceBinding` or endpoint change never swaps the visible edition and never invalidates the edition's `EditorialRevision` during the current navigation (Blueprint §99, plan #18). Source disablement, new eligibility or a new `EditorialRevision` is realized by a successor edition, never by rewriting the old one.

**D7 — A successor Edition replaces history explicitly.** Refresh, context change and lifecycle policy produce a successor edition: build its segment 0 (and the publication gate) first, then swap the active edition in a single transaction (Technical Architecture §62, Blueprint §97). The UI never observes the current edition being dismantled progressively. A failure during refresh — network, media, storage, timeout — keeps the previous edition active and usable and emits a recoverable state (plan #25). Refresh never waits for the whole catalog, every target, every stream or speculative media (Blueprint §98).

**D8 — Removal is three distinct operations, never a cascade.** (a) *Future-facing availability*: tombstones/deletion requests change `OriginRecord` availability and eligibility for new editions only (Blueprint §43, §44). (b) *Revocation of display of retained publications*: only through an explicit, recorded `PublicationOverlayPolicy` applied to a publication (Blueprint §44, plan §20.2) — the payload bytes and segment rows are unchanged. (c) *Physical purge*: an explicitly authorized user/privacy/retention purge, recorded as its own operation, may delete segment/card rows and their asset refs as one aggregate. Editorial immutability never implies infinite retention, and retention never silently deletes history (plan §9).

**D9 — `PublicationSchemaVersion` is independent.** It does not track `SelectionSchemaVersion`, editorial/connector/checkpoint versions or catalog generation (Blueprint §56, plan §19 addenda). A restore that meets an unsupported or unknown publication schema fails in a controlled way and requests a new edition; permissive interpretation of an unknown payload is prohibited.

**D10 — Media preparation happens before the commit, never inside it.** `MediaPreparation` turns `MediaCandidate[]` into a `PreparedMediaChoice` outside the transaction and outside the coordinator's isolated state (Technical Architecture §38, §42). Publication can commit with a thumbnail, poster, waveform metadata, a deterministic placeholder, or no media at all; a full audio/video download is never a publication prerequisite (Blueprint §47, §48, Technical Architecture §39, plan #22).

**D11 — Minimal local asset commit.** A local asset is committed as: write temp file → validate digest and byte count → move to its immutable content-addressed destination → make the chosen durability level hold (`fsync` of file and parent directory where the policy requires it) → reference it from the same publication transaction that publishes the card. A crash before the reference commit leaves an orphan that GC may collect; a reference to bytes that were never durably written is impossible (plan §10, Technical Architecture §64). Orphans are never adopted retroactively by a later card.

**D12 — Asset identity is digest + recipe, not URL.** `AssetVersionID` is derived from `content_digest` and `recipe_version`; `PublishedMediaRef` carries `assetVersionID`, `contentHash`, pixel dimensions, mime type and aspect ratio (Technical Architecture §65). No URL in the published payload is used as identity, as a cache key, or as a revalidation contract. Changing bytes behind a stable URL produces a new asset version, never a silently different image under the old card.

**D13 — Byte retention is pinned by publication references.** Decoded cache is discarded at any time; download cache for unpublished candidates may be evicted by quota; bytes referenced by retained publications are protected until that reference is released (plan §10). GC is mark/sweep or transactional refcounts plus reconciliation, and never removes a pinned asset (publication, draft, offline bookmark, active decode session).

**D14 — After deliberate byte removal, only identity, layout and fallback are guaranteed.** If bytes are deliberately removed (authorized purge or explicit retention decision), `asset_version` keeps digest, size, mime type and dimensions, while the card keeps its media identity, render slot, aspect ratio and a deterministic fallback. What is lost is exact pixel reproduction; that loss must be stated, not papered over (plan §20.2). Corruption is treated as the same degraded path: layout is preserved and there is no render-time download.

**D15 — `RenderContract` and render environment.** `RenderContract` fixes kind, media slot, aspect ratio and text style; render environment (width, Dynamic Type, locale) only drives materialization, never editorial history (Blueprint §17, §18, plan #16). The renderer performs zero network after publication and no blocking disk I/O or decode in a `View` body (Blueprint §105, I-02); `visual(cardID)` serves an already-materialized local asset or requests a bounded local decode.

**D16 — Actions are frozen handles, not protocol branches.** The publication freezes `primary_action_kind` plus its reference (URL, local card, media ID, thread handle, or `ActionID`) and the interaction summary. Absence of a primary action is valid, and a URL is never synthesized to satisfy a view (plan §19 addenda). Protocol-specific resolution happens behind the Session/Interaction boundary; the renderer executes a published handle (Blueprint §11, §50, §101).

**D17 — Anchors are ordinal-based.** Session restoration and window materialization use `EditionID` + `PublicationCardID` + absolute ordinal + relative offset within the card; pixel offsets are never persisted (Technical Architecture §47, plan #23). A window shift preserves the anchor in both directions and compensates for removed height without mutating published history.

## Rejected alternatives

- **Mutable published rows updated in place** (one row per origin, updated with the newest payload): rejected — violates Blueprint §57 and I-07/I-09, and destroys anchor stability; the repo already fights this by convention at `feedmine/Services/FeedStore.swift:8274-8287`.
- **Rebuilding cards at render time by joining canonical supply**: rejected — plan #20 requires the payload without a mandatory future join; canonical rows are evictable by retention (`feedmine/Services/FeedStore.swift:7255-7281`) and I-16 forbids semantic dependence on reconstructible data.
- **Swapping the active edition in place on catalog/binding/endpoint change**: rejected — Blueprint §99 keeps the `EditorialRevision` stable during navigation; only lifecycle/refresh/context change may replace history.
- **URL (or URL hash) as asset identity**: rejected — plan §10; the repo's current `ImageCacheKey.forURL` (`feedmine/Services/MediaAssetStore.swift:304-312`) is exactly the pattern being replaced.
- **Requiring full media download before publishing**: rejected — Blueprint §48 and Technical Architecture §39 allow a deterministic placeholder; tying publication to the network would move acquisition into the publication gate and stall first paint.
- **A foreign key (with or without cascade) from publication to canonical**: rejected — plan §6; it would either block authorized revision purge or let canonical deletion erase durable published history.

## Schema and types

GRDB migrator is the schema authority; `DatabasePool`, WAL and `foreign_keys = ON` on every connection, one logical writer (plan §6).

The only `ON DELETE CASCADE` edges in the publication aggregate are `published_asset_ref → published_card` (the card and its refs are one purge unit). There is no FK, and therefore no cascade, from `published_card` to `origin_record`/`origin_revision`. A schema test asserts both facts against `PRAGMA foreign_key_list`.

## Invariants

- **INV-1** No committed `feed_segment` or `published_card` payload field is ever updated; the only permitted writes are inserts of new segments/cards and the edition tail/state/pointer updates performed by `PublicationCoordinator` (I-07).
- **INV-2** Every `published_card` names exactly one `origin_revision_id` and one `publication_schema_version`, and renders its text, attribution and timestamp without reading `origin_record` or `origin_revision` (I-08, Blueprint §54).
- **INV-3** An upstream mutation, tombstone, catalog edit or source disablement changes no byte of an already committed segment (I-09, Blueprint §44).
- **INV-4** No module other than `PublicationCoordinator` (through `FeedStorage`) can insert into `feed_segment`, `published_card` or `published_asset_ref`; the append API is not exposed to connectors, `MediaPreparation`, Selection or the UI (I-10, Blueprint §57).
- **INV-5** Two commits against the same tail cannot both succeed: for any `(edition_id, segment_ordinal)` and any `(edition_id, absolute_ordinal)` there is at most one row, and a commit whose `feed_edition.version` no longer matches commits nothing (Technical Architecture §43).
- **INV-6** Deleting or expiring an `origin_record`/`origin_revision` (eviction or authorized purge) leaves every published card readable and unchanged (I-16, Blueprint §72).
- **INV-7** Every `published_asset_ref` points at an `asset_version` whose bytes reached `durability_state = 'committed'` before the publication transaction committed; there is no reachable state with a card referencing never-written bytes (Technical Architecture §64, §105).
- **INV-8** Asset identity is `(content_digest, recipe_version)`; no URL appears in `published_card` or `asset_version` as identity, cache key or revalidation input, and a URL whose bytes changed resolves to a different `asset_version_id`.
- **INV-9** After deliberate byte removal, `asset_version` retains digest, size, mime type and dimensions, and the card retains its media identity, render slot, aspect ratio and deterministic fallback; exact pixel reproduction is no longer claimed (plan §20.2).
- **INV-10** Decoded-cache eviction (including memory warnings) never changes any published asset identity or render contract (Technical Architecture §68).
- **INV-11** After publication no render path initiates network for feed cards, images, posters or visual preparation, and no `View` body performs blocking disk I/O or decode (Blueprint §105, I-02).
- **INV-12** Changing width, Dynamic Type or locale changes materialization only: `edition_id`, `publication_card_id` and absolute ordinals are unchanged (Blueprint §17, §18).
- **INV-13** `PublicationSchemaVersion` never advances because Selection, a connector, a checkpoint or an editorial revision advanced; a restore meeting an unsupported version fails in a controlled way instead of decoding permissively (Blueprint §56).
- **INV-14** A failed refresh leaves exactly one active edition — the previous one — and it remains fully navigable; the swap happens only after the successor's first segment commits, in one transaction (Technical Architecture §62, Blueprint §97).
- **INV-15** A passive catalog, `SourceBinding` or endpoint change leaves `state = 'active'` and `editorial_revision` of the current edition unchanged during the current navigation (Blueprint §99).
- **INV-16** Bookmark, read and in-flight action state live outside the published payload; no overlay write mutates a frozen column (§9, Blueprint §19).
- **INV-17** A tombstone/deletion request never deletes a segment, card or asset; suppressing the display of a retained publication requires an applied `PublicationOverlayPolicy` and is recorded (Blueprint §44).
- **INV-18** Physical purge is an explicit, authorized, recorded operation; it is never a side effect of routine retention or GC, and it never touches user state in another database (plan §9, §20.2).

## Edge cases

- Crash between temp-file write and the immutable move: no `asset_version` row exists; the temp file is an orphan, collectable, never referenced.
- Crash between asset durability and the publication commit: the asset is an orphan under cache quota; a later card that needs those bytes re-verifies the digest and either reuses the committed row or rewrites it — never a reference to missing bytes.
- Crash inside the publication transaction (before/after segment insert): the transaction is atomic, so no half-committed segment and no card without a segment.
- Crash after `COMMIT` before the session notification: the edition/segment exists and is valid; the session re-reads state on the next start and must not require a new selection to see it (plan #17).
- Tail changed between composition and commit (another coordinator, another context, a concurrent refresh): abort, release temporary pins, bounded recompose; never fit an old composition into a moved tail.
- Two coordinators, or one coordinator plus a recovered process, committing concurrently: at most one wins per tail; the loser retries against the new tail.
- Refresh failure at any stage: previous edition stays active; no partial successor is left claiming `active`; retry is bounded.
- Refresh storm: successors are built and swapped one at a time, never two `active` editions for the same `context_key`.
- Catalog edit, source disablement or endpoint change while the user is scrolling: no swap, no payload rewrite; the new eligibility takes effect in the next successor edition.
- `published_at` missing or unparsable: stored as `published_at_kind = 'none'`/`'observed'` with `observation_at_ms`; never synthesized as an authored date (Blueprint §35, plan #14).
- Content with no HTTP representation or no headline: title/primary action absent is valid; the presentation uses the primary text and an affordance that exists; no URL is synthesized.
- Media candidate that never resolves: publication commits with a deterministic placeholder, so the card is renderable offline; a late resolution must not rewrite the card.
- Duplicate candidate locators resolving to different bytes (server swap behind a stable URL): two asset versions, two digests; the already-published card keeps its own.
- Corrupted/mismatched on-disk bytes at decode time: degrade to the deterministic fallback, preserve layout, never download.
- Decoded eviction or memory warning while the user scrolls: cards keep identity, layout and pinned bytes; only decoded pixels disappear.
- Canonical revision eviction or authorized purge after publication: published cards unchanged; a bookmark or open overlay still resolves through the copied payload.
- Deliberate byte removal for a card still referenced by an offline bookmark or a retained edition: refused while a pin is active; if it proceeds under an explicit purge, the card degrades to its fallback and the loss is recorded.
- Migration to a new `PublicationSchemaVersion` while old editions exist: deterministic migration or a new edition; unknown version is a controlled failure, never permissive decode.
- Disk full during asset commit or during the publication transaction: the transaction rolls back; the previous edition stays active; the asset becomes a collectable orphan.
- Window shift at the first or last card, at a section boundary (date sections), or with large sources: anchor preserved in both directions; presentation eviction never deletes published rows.
- Fixed-edition restore where the edition is compatible but its middle segment rows were purged by an authorized purge: restore reports the gap honestly rather than renumbering.
- `ActionID` whose executor no longer offers the capability: the action is reported unavailable; the UI does not infer an action from a URL.

## Named acceptance tests

These were written as **proposed** names, following plan §19 where a row assigns one to ADR-001. **Checked 2026-09-18: they are proposals no longer** — the criteria are implemented and pinned by real tests, with the row-by-row binding in `contract-matrix.md`'s invariant table and `baseline.md` §8.54.

- `compatibleEditionRestoresWithoutSelection` — a valid edition (supported `publication_schema_version`, intact payload, compatible context) restores and displays without Selection, catalog refresh or network — PR-06/PR-07 (plan #17).
- `passiveCatalogChangeDoesNotSwapVisibleEdition` — a passive catalog/binding/endpoint change leaves the active edition and its `EditorialRevision` untouched during navigation — PR-07/PR-13 (plan #18, Blueprint §99).
- `upstreamAndCatalogEditsLeavePublishedPayloadUnchanged` — mutating an `origin_revision`, its membership/attribution, and the catalog leaves every frozen column of a published card byte-identical — PR-06 (plan #19).
- `revisionEvictionDoesNotBreakPublishedCard` — expiring the referenced canonical revision leaves the card fully renderable from its own payload — PR-06 (plan #20).
- `decodedEvictionPreservesExactPublishedAsset` — clearing the decoded cache (and a memory warning) preserves every published asset identity, render contract and pinned byte set — PR-08 (plan #21).
- `offlineCardDoesNotRequireRemotePlaybackAsset` — a card published with placeholder/no integral media renders deterministic text + geometry offline, with no network attempt for playback assets — PR-06/PR-08 (plan #22).
- `windowShiftPreservesAnchorInBothDirections` — shifting the window up and down preserves `PublicationCardID` + ordinal + relative offset and compensates removed height — PR-07/PR-13 (plan #23).
- `failedRefreshKeepsPreviousEditionVisible` — a refresh failing at each stage leaves the previous edition active, navigable and the single active edition for that context — PR-06–PR-07 (plan #25).
- `connectorAndMediaCannotAppendSegments` — a connector, `MediaPreparation` or Selection attempting to append finds no API and cannot write publication tables — PR-06 (plan #26).
- `twoCoordinatorsCannotCommitSameTail` — two coordinator instances committing against the same tail produce at most one segment/card at that ordinal, and the loser retries — PR-06 (plan #27).
- `actionExecutesWithoutProtocolBranchInView` — a card action executes through the published handle and the Interaction boundary, with no protocol switch in the view or presentation layer — PR-14 (plan #38).
- `publicationFreezesExactRevisionAndAttribution` — a publication records the exact `OriginRevisionID`, the chosen attribution/membership and the exact media version, and reproduces them from the row alone — PR-06 (added).
- `publicationSchemaVersionIsIndependentOfSelectionAndEditorialRevision` — advancing `SelectionSchemaVersion` or an editorial policy does not advance or reinterpret `PublicationSchemaVersion` — PR-06 (added).
- `unknownPublicationSchemaVersionRefusesRestore` — a payload with an unsupported publication schema version is refused with a controlled failure instead of decoded permissively — PR-06 (added).
- `assetIdentityIgnoresURLByteSwap` — same URL, different bytes yields a different asset identity, and the previously published card keeps its own asset — PR-08 (added).
- `mediaCommitFailurePublishesNoReference` — injecting failure at each step of the asset commit (temp write, digest validation, move, durability, reference) never yields a card referencing unwritten bytes — PR-06/PR-08 (added).
- `placeholderPublicationIsDeterministicAcrossLaunches` — the same card and recipe produce the same placeholder and aspect ratio on two independent runs (fixed clock/seed) — PR-06/PR-08 (added).
- `lateMediaResolutionDoesNotRewritePublishedCard` — resolving media after publication leaves the published row and ordinal unchanged, mirroring the convention currently held only in `feedmine/Services/FeedStore.swift:8274-8287` — PR-06 (added).
- `explicitUserPurgeRemovesPublicationAndAssets` — an authorized purge removes exactly the target aggregate (cards, refs, segments, unpinned assets) and reports itself as a distinct recorded operation — PR-16 (added).
- `tombstoneDoesNotDeletePublishedHistory` — a tombstone changes future eligibility only; no segment row or asset is deleted — PR-16 (added).
- `purgeRefusesWhilePinActive` — a purge or retention GC request that would remove bytes pinned by a retained edition, draft or offline bookmark is refused — PR-08/PR-16 (added).
- `dynamicTypePreservesEditionAndCardIDs` — Dynamic Type, width and locale changes alter materialization only, leaving edition and card identity stable — PR-07 (added; plan #16 assigns the row to ADR-002/ADR-001).
- `publicationTablesForbidCascadeFromOrigin` — schema-level assertion: `PRAGMA foreign_key_list(published_card)` contains no reference to `origin_record`/`origin_revision`, and the only cascade edges in the publication aggregate are within it — PR-03/PR-06 (added).
