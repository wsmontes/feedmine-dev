## Context

Runtime V2 needs one place where external protocol and network semantics live, so that Selection, Publication, FeedSession and Presentation never decode a protocol representation (Blueprint §91, §94; I-03…I-05). Today there is no such place: acquisition is a per-source pipeline in which the HTTP layer, the FeedKit parser, feed-level metadata extraction, and a network audio probe all run inside a single `fetch` call that returns `FeedFetchResult` (`feedmine/Services/RSSFetcher.swift:75-151`), validators are keyed by the editorial source URL and extracted from the *final* response of a redirect chain that URLSession follows transparently (`feedmine/Services/FeedHTTPSync.swift:118-124`, `:155-160`; `feedmine/Services/RSSFetcher.swift:122-123`; persisted in `feedmine/Services/FeedStore.swift:1305-1317`, columns at `:7990-8014`), an HTTP 200 whose parsed item list is empty still returns the updated validators (`feedmine/Services/RSSFetcher.swift:130-135`) which the scheduler then stores (`feedmine/Services/AdaptiveScheduler.swift:293-295`), concurrency is a flat per-source window with no host or purpose awareness (`feedmine/Services/RSSFetcher.swift:165-190`, called with 48/30/15/5 at `feedmine/Services/FeedStore.swift:1662`, `:4803`, `:4819` and `feedmine/Services/FeedLoader.swift:1625`), the only observable outcome at the call site is `actualNew` (`feedmine/Services/FeedLoader.swift:1625-1629`, `feedmine/Services/FeedStore.swift:1762-1776`), and the effective background entry point constructs a full app stack inside the BGTask window (`feedmine/feedmineApp.swift:55-60`; the lightweight `feedmine/Services/BackgroundRefreshService.swift` exists but is not that path). No `AcquisitionPurpose`, `AcquisitionTarget`, lease, frontier or acquisition-budget type exists in the checkout at `b5c2f59c` (symbol grep over `feedmine/**/*.swift` returns no matches). This ADR fixes the connector boundary, the finite/streaming/backfill shapes, backpressure, target sharing, endpoint and HTTP-checkpoint semantics, purpose budgets, and the read-only ingestion stance.

## Decision

**D1 — Connector boundary is DTO-only and evidence-opaque.** A connector translates protocol data into canonical, `Sendable` DTOs (`AcquisitionBatch`, `TranslatedObservation`, claims and candidates as sketched in plan §7 and Blueprint §59) plus, optionally, an opaque `ConnectorEvidence` blob. A connector MUST NOT return GRDB records, GRDB `Database` handles, FeedKit model types, SQL fragments, or closures that downstream layers have to invoke to interpret protocol semantics. Nothing downstream of Admission may decode `ConnectorEvidence` (Blueprint §85, §93; TechArch §85). Evidence is removable without changing selection or publication.

**D2 — One connector surface for finite, streaming and backfill+live.** `acquire(target:checkpoint:purpose:)` returns a bounded asynchronous sequence of batches. Finite (one batch, then finish), streaming (batches until cancellation) and backfill→live (checkpoint transition between phases) are all expressed through the same surface; no downstream layer branches on connector kind or on finite-vs-streaming (Blueprint §89, TechArch §17). Connector dispatch is a compile-time resolver in the acquisition layer only, never a universal registry (Blueprint §90, TechArch §13).

**D3 — Backpressure is real, not a buffer policy.** The acquisition stream is bounded and pull-driven: the producer cannot advance to batch N+1 until the consumer has taken batch N. Buffers are capacity-limited in batches, items and bytes. Dropping content silently is prohibited; in particular an unbounded stream (the default buffer policy of `AsyncStream`/`AsyncThrowingStream`) or any `bufferingNewest(n)` policy MUST NOT be used for the content stream. Where the protocol cannot suspend (e.g. a socket or server-push feed), the connector MUST stop with a durable checkpoint and resume from it, so that suspension is equivalent to a checkpointed stop (plan §12, §20.2). `AsyncThrowingStream` alone does not provide backpressure; it is acceptable only with an explicit acknowledgement or suspension mechanism of the above kind.

**D4 — Bounded batch and stream shape.** Maximum batches in flight per target, maximum observations per batch, maximum relations/memberships/media-candidates per observation, and maximum bytes per batch are explicit, versioned numbers checked by the connector and by Admission schema validation. A connector that would exceed a limit must split into multiple batches or stop at a checkpoint; it must not emit an oversized batch.

**D5 — Targets are operational work, not editorial identity (row #5).** `AcquisitionTarget` is a unit of work: an endpoint plus connector-owned, versioned configuration, plus a generation. The configuration stays opaque outside the connector/acquisition layer; Selection, Publication and Presentation never read it (Blueprint §24, TechArch §14). A Source may have several bindings, several targets may serve one binding, and a target MUST NOT be derived from, or compared against, editorial identity. `FeedSource.id` being the normalized fetch URL (`feedmine/Models/FeedSource.swift:11-16`) is exactly the coupling this decision removes.

**D6 — Sharing is by leases and refcounts (row #6).** Demand, not "start this target", is what the planner issues (`AcquisitionDemand`: purpose, supply deficit, priority). The planner resolves demand into leases on targets; while at least one valid lease exists the target may stay active. Abandoning one context releases only its own leases: it MUST NOT revoke another context's interest in a shared target, and it MUST NOT cancel work another live lease still needs. Real revocation (binding disabled, source removed, budget stop, mode change, expiration) bumps the target generation; a stream or batch that arrives afterwards fails in Admission as `staleTarget`/`staleCheckpoint`, even if task cancellation was not immediate (row #30; plan §12; TechArch §15-16; Blueprint §26, §64, §65).

**D7 — Frontier is finite and classified by work, not by URL (row #35).** `AcquisitionFrontier` is a finite set of active or eligible acquisition work items derived from editorial demand and budgets, classified `head`, `active`, `exploration` (Blueprint §82, §84). It is bounded per context by target budget and by the purpose budget table (D9); catalog growth increases eligibility, never simultaneously running work. The frontier is reconstructible: a crash rebuilds it from durable target/checkpoint state plus current demand (TechArch §16).

**D8 — Bootstrap is finite and terminates (row #37, §20.3).** `BootstrapPlan` ends at the first of: minimum publication gate reached, deadline reached, budget exhausted, or frontier exhausted. On exhaustion the runtime reports an explicit `exhausted` (no more supply) or `degraded` (supply exists but policy prevented fetching) state. It MUST NOT loop retrying to fill the feed, and MUST NOT delete or hide already-published history to hide exhaustion: the previously published edition and history stay navigable; retries are bounded and backoff-governed (Blueprint §85; row #37).

**D9 — Purpose budgets are explicit and per purpose (row #36, §20.3).** Each `AcquisitionPurpose` carries its own limits and its own cancellation rank. The initial numbers below are tuning baselines derived from `TechArch §18` (4 active targets, 2 per-host HTTP operations, 2 media transfers) and plan §20.3; they are not contracts and not measured results.

| purpose | target budget | request budget | byte budget | unique-host budget | connection budget | time limit | cancellation order | purpose-specific rule |
|---|---:|---:|---:|---:|---:|---:|---:|---|
| `userInitiated` | 4 | 24 | 24 MiB | 8 | 4 | 20 s | 5 (last) | keeps its limits under pressure; never preempted by lower purposes |
| `bootstrap` | 4 | 64 | 48 MiB | 16 | 4 | 25 s or publication gate | 4 | ends at the minimum publication gate without waiting for the catalog |
| `activeRunway` | 2 | 8 | 12 MiB | 4 | 2 | 15 s | 3 | serves a bounded supply deficit only |
| `speculative` | 1 | 2 | 4 MiB | 2 | 1 | 10 s | 1 (first) | first category cancelled under pressure; budget may be 0 |
| `backgroundMaintenance` | 2 | 8 | 8 MiB | 2 | 1 | remaining BGTask window | 2 | MUST NOT start work without a resumable checkpoint; respects expiration |

Counting is per purpose and per target: operations, bytes, unique hosts, redirects, open connections and wall clock. Media transfers keep a separate sub-budget (D17). A budget stop is a normal outcome, not an error: it must leave a valid checkpoint so the work resumes later (row #36).

**D10 — Endpoints, bindings and generations.** An endpoint is a network location used by a target; it is not an independent domain entity in the baseline (Blueprint §24). Endpoint changes are not Source identity changes (ADR-003). Any target configuration change whose old work would be semantically invalid bumps the target generation through the binding revision owned by ADR-006; the acquisition layer merely records and passes the generation. An endpoint change MUST NOT silently re-apply a validator obtained from the previous endpoint (D12).

**D11 — Checkpoints are opaque, versioned and connector-owned (row #28).** The runtime persists and returns `ConnectorCheckpoint` without interpreting sequence numbers, page tokens, HTTP validators, relay cursors or repo revisions (Blueprint §62, TechArch §11). A checkpoint carries connector scope, target association and a serialization schema version. Checkpoint advancement is owned by the Admission transaction, not by the connector: the connector proposes `nextCheckpoint`, and only Admission may commit it together with the accepted content of that batch (row #29 is ADR-006's; see D15 for the split).

**D12 — HTTP validator semantics.** Validators (ETag/Last-Modified) are scoped to a specific endpoint and binding revision, never to editorial Source identity, and MUST NOT be transferred blindly across a redirect to a different host or a different resource: a validator is only reusable for the endpoint that issued it. Rules:
- A `304 Not Modified` is not deletion and never removes items, availability or publication (Blueprint §43).
- A validator may be confirmed only when the response body that produced it has been admitted, or when a conditional request returns `304` on top of a baseline whose body V2 actually admitted.
- If V2 never received the body (for example a validator inherited during migration, or a supply database that was lost and rebuilt), the connector MUST perform an unconditional fetch before treating that validator as a valid checkpoint.
- A parse failure on HTTP 200 MUST NOT confirm or advance a validator.
- A successfully parsed document with zero observations may confirm a validator only when the connector can distinguish "valid document, no observations" from "parsed document whose observations could not be extracted"; the latter MUST NOT confirm a validator. Today's code returns `modifiedWithoutNewItems(validators:)` whenever the extracted item list is empty (`feedmine/Services/RSSFetcher.swift:130-135`), and the scheduler stores those validators (`feedmine/Services/AdaptiveScheduler.swift:293-295`); the connector boundary must not inherit that ambiguity. The failure path is already closer to the rule by accident: a parse failure returns `.failed(error)` without validators (`feedmine/Services/RSSFetcher.swift:144-151`) and the scheduler leaves validators untouched on `.failed` (`feedmine/Services/AdaptiveScheduler.swift:305-306`) — this ADR makes that rule deliberate instead of incidental.
- A `200` response whose body was truncated by a size ceiling MUST NOT confirm a validator (the current ceiling is a 20 MiB accumulated-body abort at `feedmine/Services/FeedHTTPSync.swift:134-146`).

**D13 — Backoff, jitter, host fairness and Retry-After.** `Retry-After` (seconds or HTTP-date, clamped) is honored globally for the target, and 429/503 map to the throttled outcome (`feedmine/Services/FeedHTTPSync.swift:106-116`; the existing clamp is at `:222-231`). Periodic cadences are never synchronized by wall clock: each target derives stable jitter from `H(localInstallationSalt, targetID, cadenceBucket)` where the salt is local, never transmitted and never part of any identity (TechArch §19, plan §20.3). The network scheduler is host-aware: per-host token bucket, per-host concurrency limit, per-host failure/backoff state, and a next-eligible time; global limits are the purpose budgets of D9. Fairness: a host that is throttled or failing MUST NOT consume the global connection budget while healthy eligible work waits, and one dominant host MUST NOT starve others.

**D14 — Hard request limits and credential hygiene.** Enforced before and during a request: scheme and host validation (only `https`; a declared `http` endpoint is upgraded or rejected, matching the current upgrade at `feedmine/Services/FeedHTTPSync.swift:57-66`), redirect-count limit, compressed-response size limit, decompressed size limit, parse time and parsed-item limits, batch item limits (D4). Query strings are never logged (signed URLs and tokens are personal data per plan §1). Credentials or authorization headers are never attached by this core: there is no credential path (D19), and no header may be forwarded to a redirected host other than the origin's own redirect semantics.

**D15 — Result taxonomy: connector failure vs Admission outcome.** The connector reports transport, protocol and translation facts; Admission alone decides canonical outcomes. Ownership:

| outcome | owner | meaning |
|---|---|---|
| `batch` (DTOs) | connector | translated observations with `TranslationOutcome` per observation |
| `notModified` / `redirected(endpoint:)` / `throttled(until:)` / `transportFailure(class:)` / `parseFailure` / `translationRejected(reason:)` / `endOfFinite` / `streamEnded(cancelled:)` | connector | never mutates canonical state; may update cadence, health and bounded diagnostics |
| `admitted` | Admission (ADR-006) | content committed, checkpoint advanced in the same transaction |
| `duplicate` | Admission | same batch fingerprint or same revision already present; no spurious supply increment |
| `staleTarget` | Admission | target revoked, generation/binding/lease no longer current |
| `staleCheckpoint` | Admission | expected checkpoint revision does not match; batch is not applied |
| `identityConflict` | Admission | same external version key with divergent payload, or ambiguous alias |
| `invalidObservation` | Admission | schema/limit violation in a batch or observation |
| `storageFailure` | Admission | transaction failed; nothing partial survives |

A connector MUST NOT report `admitted`/`duplicate`/`stale*` and MUST NOT touch canonical tables; Admission MUST NOT parse protocol payloads to decide these outcomes (row #35 of Blueprint §122 for the split; ADR-006 owns the transaction).

**D16 — Partial errors and all-or-nothing pages.** The default for paginated/finite checkpoints is all-or-nothing: a batch that fails validation is wholly rejected and the checkpoint does not advance (row #28). A connector that wants per-item durable rejection must declare it in its contract, and the checkpoint may only advance if the resume contract proves no valid item was lost. Admission records either a durable per-item rejection or nothing; a partially applied batch is a defect (plan §7).

**D17 — Media speculation is not acquisition.** Probing audio/video playability is MediaPreparation work, not connector work (Blueprint §92, §46): acquisition must not delay a batch on per-item network probes. The current pipeline does exactly that (`validateAudio` inside `fetch`, `feedmine/Services/RSSFetcher.swift:136`, implementation at `:421-454` with up to 12 probes and 6 concurrent, `probeAudio` at `:498`); the connector boundary MUST NOT inherit it. Media transfers keep their own sub-budget, separate from the purpose budget above.

**D18 — Measurement is separated and network health is not editorial quality.** HTTP outcome, translation and Admission are measured as three separate stages with correlation IDs; a connector failure marks cadence/backoff and target health, never a score, ranking or eligibility input (I-17; Blueprint §78). Transport latency is never a quality signal.

**D19 — Read-only/ingestion stance (row #39).** The Feed Runtime is a read/ingestion runtime: no protocol write, no federation participation, no universal credential store, no account framework in the core (Blueprint §51, §52). Interaction offers are local capabilities with an `ActionID` handle, ready for extension, and their execution belongs to Session/Interaction (ADR-001, ADR-007), never to a connector. `FeedConnector` has no write method; a future write capability must be a separate, explicitly-scoped type outside the core.

**D20 — Parser isolation without general escape hatches.** A non-`Sendable` parser (FeedKit and future SDK equivalents) is created *and* consumed on the worker that owns the parse; only `Sendable` DTOs cross the boundary. A general `@unchecked Sendable` conformance to make a parser type passable is prohibited; a narrowly documented, audited exception requires a dedicated review entry and is not the default solution (plan §12; Blueprint §91).

## Rejected alternatives

- **Universal protocol adapter framework / connector registry.** Rejected: it invents an abstraction before a second ecosystem exists and invites protocol branches downstream; a compile-time resolver in the acquisition layer is enough (Blueprint §90, TechArch §13).
- **`AsyncThrowingStream` with default or unbounded buffering.** Rejected: `bufferingNewest` drops content silently under pressure and no buffer size provides backpressure; a pull/ack or checkpointed stop is required (plan §12, §20.2).
- **One target per Source, or one connection per Source.** Rejected: it turns a large catalog into per-source network tasks and makes sharing impossible; targets are shared work with leases (Blueprint §25, TechArch §15).
- **Reusing `(items, validators)` as the acquisition outcome and keying validators by source URL.** Rejected: it makes a 200-with-nothing-extracted confirm a validator, and it transfers validators across redirects to changed endpoints; validators are endpoint/binding-scoped and confirmation requires admitted content (D12).
- **Letting the acquisition path probe media playability.** Rejected: it couples batch latency to per-item network work that belongs to MediaPreparation (Blueprint §92).
- **A credential/write path in the core to "future-proof" connectors.** Rejected: it contradicts the read/ingestion baseline and creates federation/credential surface the product does not need now (Blueprint §51, §52).

## Schema and types

SQLite fragments use the plan §6 naming and the table set of TechArch §25. Runtime database: `runtime-v2.sqlite` (plan §6).

```sql
CREATE TABLE acquisition_target (
    id                INTEGER PRIMARY KEY,
    connector_kind    TEXT    NOT NULL,
    configuration_fp  BLOB    NOT NULL,          -- digest of connector-owned config
    configuration_blob BLOB   NOT NULL,          -- opaque outside connector/acquisition
    generation        INTEGER NOT NULL DEFAULT 1,
    lease_count       INTEGER NOT NULL DEFAULT 0,
    state             TEXT    NOT NULL
        CHECK (state IN ('candidate','requested','active','draining','revoked',
                         'exhausted','backoff')),
    failure_class     TEXT,
    next_eligible_at  INTEGER,
    last_success_at   INTEGER,
    last_attempt_at   INTEGER,
    UNIQUE (connector_kind, configuration_fp)
);

CREATE TABLE acquisition_lease (
    id            INTEGER PRIMARY KEY,
    target_id     INTEGER NOT NULL REFERENCES acquisition_target(id) ON DELETE CASCADE,
    holder_id     TEXT    NOT NULL,              -- context/plan/edition demand owner
    purpose       TEXT    NOT NULL
        CHECK (purpose IN ('userInitiated','bootstrap','activeRunway',
                           'speculative','backgroundMaintenance')),
    priority      INTEGER NOT NULL,
    generation    INTEGER NOT NULL,              -- generation observed at lease time
    created_at    INTEGER NOT NULL,
    released_at   INTEGER,
    UNIQUE (target_id, holder_id, purpose)
);

CREATE TABLE connector_checkpoint (
    id                INTEGER PRIMARY KEY,
    target_id         INTEGER NOT NULL REFERENCES acquisition_target(id) ON DELETE CASCADE,
    connector_kind    TEXT    NOT NULL,
    schema_version    INTEGER NOT NULL,
    payload           BLOB    NOT NULL,          -- opaque to the core
    payload_fp        BLOB    NOT NULL,
    committed_revision INTEGER NOT NULL DEFAULT 0,  -- CAS token owned by Admission
    updated_at        INTEGER NOT NULL,
    UNIQUE (target_id, connector_kind)
);

CREATE TABLE admission_batch (
    id              INTEGER PRIMARY KEY,
    batch_fp        BLOB    NOT NULL,
    target_id       INTEGER NOT NULL REFERENCES acquisition_target(id),
    target_generation INTEGER NOT NULL,
    checkpoint_id   INTEGER REFERENCES connector_checkpoint(id),
    expected_checkpoint_revision INTEGER NOT NULL,
    received_at     INTEGER NOT NULL,
    result          TEXT    NOT NULL,
    UNIQUE (batch_fp)
);

CREATE TABLE connector_evidence (
    id                INTEGER PRIMARY KEY,
    target_id         INTEGER NOT NULL REFERENCES acquisition_target(id) ON DELETE CASCADE,
    origin_record_id  INTEGER,
    schema_version    INTEGER NOT NULL,
    payload           BLOB    NOT NULL,          -- raw/compressed, retention per ADR-004
    created_at        INTEGER NOT NULL
);

-- Per-request accounting; also the durable stop point for a budget stop.
CREATE TABLE acquisition_usage (
    id           INTEGER PRIMARY KEY,
    target_id    INTEGER NOT NULL REFERENCES acquisition_target(id) ON DELETE CASCADE,
    purpose      TEXT    NOT NULL,
    window_start INTEGER NOT NULL,
    requests     INTEGER NOT NULL DEFAULT 0,
    bytes        INTEGER NOT NULL DEFAULT 0,
    hosts        INTEGER NOT NULL DEFAULT 0,
```

Swift contract sketch (proposals; `AcquisitionBatch`/`TranslatedObservation` per plan §7 and Blueprint §59):

```swift
public enum AcquisitionPurpose: String, Sendable, CaseIterable {
    case userInitiated, bootstrap, activeRunway, speculative, backgroundMaintenance
}

public struct AcquisitionDemand: Sendable {
    public let purpose: AcquisitionPurpose
    public let priority: DemandPriority
    public let deficit: SupplyDeficit          // context + desired sequenceable distance
}

public struct AcquisitionTarget: Sendable {
    public let id: AcquisitionTargetID
    public let connectorKind: ConnectorKind
    public let generation: UInt64              // bumped on revocation/config change
    public let configuration: ConnectorTargetConfiguration  // opaque outside acquisition
}

public struct ConnectorCheckpoint: Sendable, Codable {
    public let connectorKind: ConnectorKind
    public let schemaVersion: Int
    public let payload: Data                   // opaque to the core
}

public enum ConnectorResult: Sendable {
    case batch(AcquisitionBatch)
    case notModified(endpoint: EndpointID)
    case redirected(to: EndpointID)                       // validator is NOT reused
    case throttled(until: Date)
    case transportFailure(TransportFailureClass, retryable: Bool)
    case parseFailure(truncated: Bool)
    case translationRejected(ExternalObjectKey, TranslationRejectionReason)
    case endOfFinite
    case streamEnded(cancelled: Bool)
}

public protocol FeedConnector: Sendable {
    /// Bounded, pull-driven: the producer suspends until the consumer takes the
    /// previous batch, or stops at `nextCheckpoint` when the protocol cannot suspend.
    func acquire(
        target: AcquisitionTarget,
        checkpoint: ConnectorCheckpoint?,
        purpose: AcquisitionPurpose
    ) -> AcquisitionStream
}

/// Buffer limits are explicit; never `bufferingNewest` for content.
public struct StreamLimits: Sendable {
    public let maxBatchesInFlight: Int   // 1 in the baseline implementation
    public let maxObservationsPerBatch: Int
    public let maxBytesPerBatch: Int
}
```

**Lease state table (target lifecycle):**

| state | who holds it | what it permits | what revokes / leaves it |
|---|---|---|---|
| `candidate` | nobody; derived from catalog + demand | nothing (no network) | demand resolution revokes it by creating a lease |
| `requested` | planner holds a demand, no lease yet | nothing (no network) | demand withdrawn, budget stop -> back to `candidate` |
| `active` | ≥1 live lease (`acquisition_target.lease_count > 0`) | one stream/request at a time for that target | a lease release decrements the count; the target leaves `active` only when the count reaches 0 |
| `draining` | coordinator during expiration/termination | in-flight work completes or is cancelled; committed receipts stay valid | drain completes -> `candidate` (or `revoked`) |
| `revoked` | runtime after disable/removal/binding change/mode change; generation bumped | nothing; late streams fail as `staleTarget` | explicit re-enable creates a new generation |
| `exhausted` | frontier, when a finite plan has no further work | nothing for that plan; history stays navigable (D8) | new demand or new binding revision |
| `backoff` | network scheduler after failure/`Retry-After` | nothing until `next_eligible_at` | eligibility time reached, or purpose `userInitiated` after explicit user action |

**Purpose budget table:** see D9 (this is the normative copy for citations from other ADRs).

**OPEN (must be closed elsewhere before the corresponding core code):**
- `OPEN:` exact numeric values of `StreamLimits` and the batch/byte ceilings, to be fixed after the PR-00 baseline measurement — this ADR (D4) plus ADR-004 for storage-side limits.
- `OPEN:` whether `acquisition_lease` is durable or purely ephemeral coordination (TechArch §16 says coordination is ephemeral while `acquisition_target` is durable). Owner: ADR-006; D6 above requires only that generation and revocation survive restart, which `acquisition_target` can carry.
- `OPEN:` retention class and TTL of `connector_evidence` and of `acquisition_usage` rows. Owner: ADR-004.
- `OPEN:` whether `acquisition_usage` windows are per purpose only or per purpose×host, and the reset boundary. Owner: this ADR at freeze; no core code may depend on it before it is closed.
- `OPEN:` the durable representation of "V2 has never received a given endpoint's body" (D12) — a per-endpoint marker table or a flag inside `connector_checkpoint`. Owner: ADR-004 (durability) with ADR-006 (transaction).
- `OPEN:` media sub-budget numbers (D17). Owner: ADR-001/ADR-004 with PR-08.

## Invariants

1. **INV-1** No connector returns a GRDB record, a FeedKit/SDK model type, or a closure downstream layers must call to interpret protocol semantics; a boundary test compiles against DTO types only. (I-18)
2. **INV-2** No layer outside the acquisition/connector targets decodes `ConnectorEvidence`; removing all evidence rows changes no selection, publication or presentation output. (Blueprint §85; I-03…I-05)
3. **INV-3** The content stream never drops a batch silently: with the consumer stopped, the producer's in-flight batch count never exceeds `maxBatchesInFlight` and no batch is discarded by buffer policy. (I-19)
4. **INV-4** Releasing one lease never cancels or revokes work that another live lease on the same target still needs; a target stops only when `lease_count` reaches 0 or it is revoked. (I-12)
5. **INV-5** After a revocation bumps the generation, any batch produced from the previous generation fails Admission with `staleTarget` or `staleCheckpoint` and mutates no canonical row, no projection and no checkpoint. (I-12, I-11)
6. **INV-6** A checkpoint revision in `connector_checkpoint` is never greater than the progress durably admitted for that target; no connector writes it directly. (I-11)
7. **INV-7** A validator is never applied to an endpoint other than the one that issued it, and a redirect that changes host or resource never reuses the previous endpoint's validator. (I-17)
8. **INV-8** A parse failure, a truncated body, or a document whose observations could not be extracted leaves the validator and checkpoint unchanged; only an admitted body or a `304` over an admitted baseline may confirm a validator. (I-11, I-17)
9. **INV-9** A `304` never removes an item, changes availability, or alters publication. (I-09 via ADR-001)
10. **INV-10** Every acquisition request is attributed to exactly one purpose and is counted (requests, bytes, hosts, redirects, connections) against that purpose's budget; no request is issued outside a budget. (I-19)
11. **INV-11** A budget stop, deadline or expiration leaves either no durable change or a valid checkpoint that resumes the same work; it never leaves a corrupted or ahead-of-content checkpoint. (I-19, I-11)
12. **INV-12** Escalating concurrency with catalog size does not increase concurrently running acquisition work: running targets stay bounded by demand and purpose budgets. (I-19)
13. **INV-13** When a finite plan is exhausted, the runtime reports `exhausted`/`degraded` and performs no unbounded retry loop; previously published editions and history remain readable. (I-16, I-19)
14. **INV-14** No per-source or per-observation transport work (including media probing) occurs inside a batch's production path. (Blueprint §92; I-02 boundary spirit)
15. **INV-15** The core exposes no write, follow, post, or credential-storage dependency: `FeedConnector` has no write member and no core module imports a credential or federation write API. (Blueprint §51, §52)
16. **INV-16** A non-`Sendable` parser value never crosses the connector boundary; no general `@unchecked Sendable` conformance is used to pass parser or model types across it. (I-18)
17. **INV-17** A connector failure changes cadence, backoff state and health only; it changes no editorial score, ranking or eligibility. (I-17)
18. **INV-18** Adding a second connector kind requires no edit in Selection, Publication, FeedSession or Presentation: those modules compile unchanged. (I-03…I-05, Blueprint §123)

## Edge cases

- Cancellation is not immediate: a stream may emit after the lease was released. Valid generation check at Admission must reject it (D6).
- Process death between network completion and Admission commit: batch is lost, checkpoint did not advance, refetch is the recovery path.
- Process death after Admission commit but before the connector learned the outcome: replay of the same batch fingerprint must be a no-op `duplicate`, not a supply increment.
- Budget exhausted mid-page: the connector must stop at the last safe boundary and write a resumable checkpoint; a partially consumed page must not be claimed as consumed.
- Budget stop during a streaming connector with no suspension support: stop and resume from the checkpointed position — never keep reading and discard.
- Two contexts share a target, one switches context mid-flight: the remaining lease keeps the target active; the switched-away context's demand is dropped, not the target.
- Disable then re-enable a source: the re-enable produces a new binding revision and therefore a new target generation; old streams must not satisfy the new demand.
- Server returns `304` after V2 lost its supply (rebuilt database, migrated validator): unconditional fetch required first (D12); never treat the `304` as "nothing exists".
- Server returns `200` with a body whose parse yields zero extractable observations: validator unchanged (D12); the target may later produce content.
- Server returns a redirect to a different host on every request: redirect-count limit stops the work; validators from the previous endpoint are discarded.
- Clock skew and DST transitions: deadlines use a monotonic clock; `Retry-After` HTTP-dates are clamped; jitter uses `cadenceBucket`, not wall-clock alignment.
- A host is throttled (429/503) while other hosts are healthy: throttled host exhausts only its own per-host budget; global connection budget stays available for fair work.
- Very large compressed response with high expansion ratio: decompressed-size limit aborts the request and the validator is not confirmed.
- A feed whose items all lack external IDs: the connector still emits observations; identity resolution belongs to ADR-003/Admission (`identityConflict`/fallback), never a connector-local silent drop.
- The second-paradigm fixture emits a versioned stream with relations and offers: it must flow through the same Admission and the same runtime, with no downstream change.
- Media probe deferred to MediaPreparation means a card may publish without audio/video being validated: the playability outcome must degrade the media candidate, not the observation.
- Expiration during background maintenance: cancel producers, release leases where applicable, complete the BGTask exactly once; work already committed stays valid.
- No supply at all (all targets exhausted or disabled): explicit `exhausted`/`degraded` state, no loop; existing edition and history still render.

## Named acceptance tests

Future tests; none of these exists at `b5c2f59c`. Names in the first block are the exact names proposed in plan §19 for this ADR.

- `targetIsIndependentOfSourceIdentity` — changing a target's endpoint/config does not change any Source identity and two Sources may map to one target — FeedDomain + FeedRuntime/Acquisition (plan §19 #5, PR-10).
- `twoSourcesShareTargetWithoutDuplicateWork` — two demands resolving to one target produce one stream and one set of requests, and releasing one lease keeps the other alive — FeedRuntime/Acquisition + FeedStorage (plan §19 #6, PR-10).
- `revokedStreamCannotMutateSupply` — a batch from a revoked generation fails as `staleTarget` and leaves canonical supply, projections and checkpoint untouched — FeedStorage/Admission (plan §19 #30, PR-03/10).
- `invalidBatchDoesNotMutateCanonicalState` — an oversized/schema-invalid batch is wholly rejected with `invalidObservation` and the checkpoint does not advance — FeedStorage/Admission (plan §19 #28, PR-03).
- `olderRevisionRemainsHistoricalAfterNewerCurrent` — a late older revision arriving after a newer current revision is stored as history, not promoted — FeedStorage/Admission (plan §19 #31, PR-03/11).
- `frontierRemainsBoundedUnderCatalogGrowth` — growing the catalog from 1k to 100k sources does not increase concurrently running targets or open connections — FeedRuntime/Acquisition (plan §19 #35, PR-10).
- `purposeBudgetStopsAcquisitionWithoutLosingCheckpoint` — exhausting a purpose budget stops the work, records the usage, and leaves a checkpoint that resumes the same position — FeedRuntime/Acquisition + FeedStorage (plan §19 #36, PR-10/15).
- `noSupplyDoesNotLoopOrEraseHistory` — with all targets exhausted the runtime reports `exhausted`/`degraded`, issues no further requests, and the published edition plus history remain readable — FeedRuntime/Acquisition + FeedRuntime/Publication (plan §19 #37, PR-09/13).
- `coreHasNoUniversalProtocolWriteDependency` — no core module declares a write/follow/post/credential dependency; the boundary test fails if one is added — FeedDomain/FeedRuntime boundary test (plan §19 #39, PR-01/10).
- `versionedStreamingConnectorUsesUnchangedRuntime` — a fake versioned streaming connector with relations, provenance and offers flows through the unchanged Admission/Selection/Publication/Session path — FeedRuntime + FeedStorage (plan §19 #40, PR-10, repeated in PR-17).
