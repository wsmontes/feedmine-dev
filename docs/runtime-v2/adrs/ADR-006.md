# ADR-006 — Concurrency/Admission

**Blueprint §115 name:** Concurrency, Idempotency & Write Admission.
**Status:** Proposed — freeze pending sign-off (Gate 0 not complete).
**Date:** 2026-09-17. **Base:** `b5c2f59c`, branch `fix/release-1.0-final-hardening`.

Approval of this ADR happens outside it: plan §1 states the current task authorised a plan review, not the
migration, and the §19 preamble presents the 40 rows as "a proposta para o freeze". Nothing below is accepted,
approved or implemented, and Gate 0 is not declared complete because this file exists.

## Context

Runtime V2 must turn untrusted, late, replayed and concurrently delivered upstream observations into canonical
supply without ever corrupting durable state: the Technical Architecture makes this the whole point of
"transactional admission" (§21–§23, §28) and the Blueprint fixes the two load-bearing invariants I-11
("Admission checkpoint cannot advance beyond admitted content") and I-12 ("Stale target generation cannot mutate
canonical supply"). Today's codebase offers no equivalent machinery, so every rule below is a new obligation
rather than a preserved behaviour. The facts that force the decision:

- `feedmine/Services/FeedStore.swift:4628-4658` — `persistFetchedItems` runs inside one `db.write`, but the row loop catches per-item errors and continues (comment at `:4646`: "One bad row does not roll back the batch"), so today's "batch" is partial-success; its callers nevertheless treat it as all-or-nothing and slice large batches at `feedmine/Services/FeedStore.swift:2309-2318`. Neither reading may be assumed by Admission.
- `feedmine/Services/FeedStore.swift:3641-3645` — stale-work rejection is an in-memory `generation == searchGeneration` comparison performed *after* `persistFetchedItems` already committed; the canonical write is not gated by the generation check at all.
- No durable stamp exists: `feedmine/` contains zero matches for `CREATE TRIGGER`, `BEFORE UPDATE`, `expectedRevision` or `compareAndSwap` (grep-verified). Nothing protects an append-only table, so `origin_revision` immutability (I-06) and the current-revision CAS have nothing to build on.
- `feedmine/FeedEngine/SQLiteCatalogStore.swift:65-76` — the catalog is compiled into a temporary database file and installed by `replaceItemAt`/`moveItem`; readers open it with `DatabaseQueue` (`feedmine/FeedEngine/SQLiteCatalogStore.swift:348`). The catalog is replaceable state, not a transactional participant, and Admission may not read it inside a write transaction.
- `feedmine/Services/UserStateStore.swift:176` holds `user.sqlite` in its own `DatabaseQueue` with `journal_mode = WAL` and `foreign_keys = ON` per connection (`:186-188`), and writes its migration markers in the same transaction as the migrated rows (`:458-464`). No commit spans `user.sqlite` and any runtime database (plan §5.2).
- `feedmine/Services/FeedStore.swift:3822-3827` — durable user actions are fire-and-forget `Task { try await db.write { … } }`; the failure is never observed. Uncoordinated writes are the current norm.
- `feedmine/Services/FeedDisplayState.swift:427-437` is the one existing precedent for a persisted fingerprint: SHA-256, explicitly *not* `hashValue`, because Swift seeds `hashValue` per process. Admission fingerprints must follow that precedent, not the `hashValue` idiom.

## Decision

**D1 — Every canonical write is guarded by a `TargetStamp` validated inside the write transaction.** After
`BEGIN IMMEDIATE` and before the first mutation, the transaction reads `acquisition_target` and
`connector_checkpoint` and compares them to the stamp: target row exists and `state != 'revoked'`;
`stamp.targetGeneration == generation`; `stamp.bindingRevision == binding_revision`;
`stamp.leaseEpoch == lease_epoch` (revocation and disable/re-enable bump the epoch, so late work from a revoked
context fails); `stamp.checkpointRevision == checkpoint_revision`. Any mismatch aborts with `staleTarget` or
`staleCheckpoint` and no mutation. Validation performed when the work was *scheduled* is an optimisation only:
validity is decided at write admission (Blueprint §26, §64).

**D2 — Admission batch identity is `batchID` + fingerprint, with defined replay semantics.** The connector
supplies a `batchID` that is stable across retries; the runtime computes a fingerprint as SHA-256 over a
canonical serialisation of the batch body (observations, memberships, relations, media, offers, target
generation, binding revision, next checkpoint). Same `batchID` + same fingerprint ⇒ `replayed`: zero canonical
mutations, zero SupplyGeneration increment, and the stored receipt is returned. Same `batchID` + different
fingerprint ⇒ `batchConflict`, no mutation, logged as an audited conflict. The fingerprint and receipt are
persisted before the transaction returns, so a retry after a lost response is answerable from durable state
alone; if the receipt row has been evicted (ADR-004 window) while the checkpoint is already ahead of the batch's
expected checkpoint, the batch degrades to `staleCheckpoint` — eviction can therefore never cause double
application.

**D3 — Precedence reaches the core only as closed instructions.** `RevisionPrecedence` is exactly
`makeCurrent(expectedRevision: OriginRevisionID?)`, `historicalOnly` and `duplicate(of: OriginRevisionID?)`. The
core executes a generic compare-and-swap for `makeCurrent` and records the revision in the other two cases; it
never parses RSS/Atom, never compares headlines, URLs or timestamps, and has no `protocol ==` branch to choose
precedence (Blueprint §63, tech arch §28, §107 I-03–I-05). Unconditional replacement is not expressible: a
connector that wants to overwrite must carry the revision it believes current, which it obtained from an earlier
admission receipt or a fresh read of current state through the connector boundary.

**D4 — Three orders stay separate.** Acquisition generation is operational validity of work; checkpoint
revision is progress through an external stream; editorial revision precedence is content currency. A checkpoint
may legitimately advance on a batch whose observations are all `historicalOnly`, and an observation may arrive
later than another while representing older content. Without a trustworthy version or timestamp from the
connector, the runtime does not promise universal semantic-regression detection; when two external versions are
not comparable, the observation is preserved as a revision and the current pointer is not silently overwritten
(Blueprint §30, §63; plan §7).

**D5 — Checkpoint advances by CAS and never outside the admitting transaction.** `connector_checkpoint` holds
one row per target with a runtime-owned monotone `checkpoint_revision` and an opaque `checkpoint_blob`
(Blueprint §62). The only mutation is `UPDATE … WHERE target_id = ? AND checkpoint_revision = ?` with the value
from the stamp; `changes() = 0` ⇒ `staleCheckpoint` and rollback. The checkpoint is written in the same
transaction that admits or durably rejects the content it represents, so a checkpoint ahead of committed
progress is a hard failure, not a tolerable average (Blueprint §61, I-11; plan §16 target 0).

**D6 — `SupplyGeneration` increments at most once per transaction and only when relevant supply changed.**
Increment when a new revision becomes current, when the current pointer moves, when membership, availability or
a relation changes selectability, or on an authorized removal; do not increment for `replayed`, in-batch
`duplicate`, `historicalOnly` without a membership/eligibility change, `staleCheckpoint`, `batchConflict` or
`invalidBatch`. `selection_supply` is updated in the same transaction as canonicalization, and a read captures
pool and generation from one SQLite snapshot (plan §6, tech arch §23).

**D7 — All-or-nothing is the default for page checkpoints, with a bounded alternative.** A batch with any
invalid observation mutates nothing and does not advance the checkpoint. Batch size is bounded by observation
count and bytes; the connector splits pages, and an oversized batch is `invalidBatch` without checkpoint
advance, so transactions cannot grow unbounded. The alternative durable per-item rejection contract
(`admission_rejection` rows written in the same transaction, checkpoint advanced past the rejected items) is
allowed only for a connector kind whose resumption contract proves that no valid item was skipped, and is
opt-in per connector kind, off by default (plan §7).

**D8 — No suspension, network, parse, decode or foreign callback inside the write transaction.** The
transaction body is a synchronous, non-suspending closure over already-decoded `Sendable` values. No `await`, no
`URLSession`, no FeedKit parser, no `JSONDecoder`, no ImageIO, no actor hop, no escaping callback, no user code
injected by a connector. All translation happens before admission and all media work happens after it; holding
the single writer connection across a suspension would serialise the database behind network latency and invite
spurious `SQLITE_BUSY` (tech arch §24, §42; plan §7).

**D9 — Cancellation saves work; commit validation provides safety.** A task cancelled before its transaction
starts is abandoned without touching the database. A task that reaches the transaction is admitted or rejected
purely by the D1 validations — cancellation neither grants nor removes authority (Blueprint §64). A
`COMMIT` that already returned is final even if the task is cancelled, the coordinator actor is gone or the
in-memory event was never delivered; later sessions learn about it by reading durable state, never from memory
(Blueprint §77).

**D10 — Reentrancy and retries.** `AdmissionEngine` is a value type, not an actor; concurrent callers are
serialised by SQLite's write lock, not by domain code. One logical writer per database (`DatabasePool` + WAL, one
writer at a time, plan §6). Retryable: `storageFailure` only, and the retry must re-read target, checkpoint and
receipt state before rebuilding the stamp. Non-retryable: `staleTarget`, `staleCheckpoint`, `batchConflict`,
`identityConflict`, `invalidObservation` — these require new work, not another attempt. Retrying a batch whose
commit succeeded must reuse the same `batchID` and fingerprint and therefore returns `replayed`. Backoff is
bounded and jittered, applied outside the transaction (tech arch §19).

**D11 — `RuntimeWriteCoordinator` admits only non-critical writes.** The coordinator batches exposure facts,
telemetry, source-health and diagnostic counters, with a baseline flush of 20 facts or 500 ms plus lifecycle
transitions (tech arch §74, plan §12). It never accepts an Admission commit, a Publication commit, a checkpoint
advance or a durable user action, and exposes no API whose parameter type is one of those; those four remain
explicit commits performed by their owners.

**D12 — Failures are typed and each type has a fixed effect on canonical state and checkpoint.**

| Result | Canonical state | Checkpoint | Retryable |
|---|---|---|---|
| `admitted` | mutated | advanced by CAS | — |
| `replayed` | unchanged | unchanged | no |
| `duplicate` (observation) | unchanged for that observation | per batch result | no |
| `staleTarget` | unchanged | unchanged | no; needs new work |
| `staleCheckpoint` | unchanged | unchanged | no; re-read then re-acquire |
| `batchConflict` | unchanged | unchanged | no; audited conflict |
| `identityConflict` | unchanged | unchanged | no; ADR-003 owns resolution |
| `invalidObservation` | unchanged (all-or-nothing) | unchanged | no; connector must fix or split |
| `storageFailure` | unchanged (rollback) | unchanged | yes, after re-reading the stamp |

Aggregated logs distinguish identity/conflict rejections from transport failures so a broken feed is never read
as a network problem (plan §7).

**D13 — Stale work leaves no canonical residue.** Default for work failing D1–D5: no canonical mutation, no
membership, no relation, no projection, no checkpoint, no exposure. Permitted residue: bytes already downloaded
and content-addressed, kept only as orphan cache under quota (ADR-004 owns retention), and non-sensitive
aggregate diagnostics/counters. Cache presence never authorises retroactive association of an asset or revision
to a record (plan §19 additional rows: stale work rejects every canonical, checkpoint and projection mutation).

**D14 — Append serialization belongs to `PublicationCoordinator`.** Only the coordinator exposes append (I-10);
it establishes single-flight per edition and, after the long work ran outside actor isolation, re-reads the tail
and validates `PublicationToken` (edition, epoch, editorial revision, expected tail) inside the publication
transaction (tech arch §41–§43). Single-flight is an optimisation, not the guarantee: the guarantee is the tail
re-read plus `UNIQUE(edition_id, segment_ordinal)` and `UNIQUE(edition_id, absolute_ordinal)`, which hold even
with two coordinator instances or a crash-restarted one. Connectors and media have no insert path into
`feed_segment`/`published_card`, and the boundary test denies one. A tail conflict discards the composition,
releases draft pins and recomposes with bounded retry; no stale draft is silently renumbered (plan §9).

### Transaction procedure (SQL level) and behaviour if the process dies after each step

```text
BEGIN IMMEDIATE
 1  SELECT state, generation, binding_revision, lease_epoch FROM acquisition_target WHERE id = :target
 2  SELECT checkpoint_revision FROM connector_checkpoint WHERE target_id = :target
 3  SELECT fingerprint, receipt_blob FROM admission_batch WHERE batch_id = :batchID
 4  SELECT id, current_revision_id FROM origin_record WHERE connector_scope_id = ? AND external_object_fp = ?
 5  INSERT INTO origin_revision (…)                       -- new representations only
 6  UPDATE origin_record SET current_revision_id = :new
       WHERE id = :record AND current_revision_id IS :expected   -- CAS
 7  INSERT/UPDATE memberships, provider attribution, relations, media candidates, offers
 8  UPDATE/INSERT selection_supply for affected records; refresh FTS rows for those records
 9  INSERT INTO admission_batch (…)                        -- receipt, fingerprint, result
10  UPDATE connector_checkpoint SET checkpoint_revision = checkpoint_revision + 1, checkpoint_blob = :blob,
       serialization_schema = :v, connector_version = :cv, updated_at = :now
       WHERE target_id = :target AND checkpoint_revision = :expected
11  UPDATE supply_generation SET value = value + 1 WHERE id = 1   -- only if step 5/7/8 changed selectable supply
COMMIT
    emit AdmissionResult; invalidate runway/selection estimates for the affected generations
```

| Dies immediately after | Durable state on reopen |
|---|---|
| `BEGIN IMMEDIATE` | No commit record in the WAL; the write transaction is rolled back. Target, checkpoint, supply: unchanged. The batch may be re-delivered under the same `batchID` and is admitted normally. |
| Step 1 (target read) | Rollback to identical state; nothing has been written and no lock survives recovery, so the batch is admitted normally on re-delivery. |
| Step 2 (checkpoint read) | Identical; the checkpoint is unchanged, so the batch's expected revision is still valid. |
| Step 3 (batch receipt read) | Identical; no receipt exists, so a retry is a first admit rather than a replay. |
| Step 4 (identity resolution) | Rollback. No `origin_record` row exists and no ID is reserved; rowid reuse is harmless. |
| Step 5 (`origin_revision` inserts) | Rollback: no revision rows survive. No revision may exist without its admitting transaction. |
| Step 6 (current-revision CAS) | Rollback: the current pointer is exactly as before, so no card can later see a revision that was never committed. |
| Step 7 (relations/memberships/media/offers) | Rollback: no membership or attribution is applied without the revisions they describe. |
| Step 8 (`selection_supply`/FTS) | Rollback: the projection equals canonical state; there is no window in which supply is selectable before it is canonical. |
| Step 9 (receipt row) | Rollback: no receipt exists and no canonical effect exists. The retry is a first admit, not a replay. |
| Step 10 (checkpoint update) | Rollback: this is the case Blueprint §61 forbids in the other order — checkpoint 850 without content up to 850 cannot occur, because checkpoint and content share one transaction. |
| Step 11 (supply generation) | Rollback, same as step 8: generation never advances for supply that was not committed. |
| `COMMIT` returned, before the `AdmissionResult` is emitted | The commit is authoritative. No correctness property depends on the in-memory event; the next session rebuilds from `acquisition_target`, `connector_checkpoint`, `origin_record`/`current_revision_id` and `admission_batch` (Blueprint §77). A resent batch returns `replayed`. |

Power-loss durability depends on the `synchronous` policy and WAL syncing, which plan §15.1 explicitly says a
process kill does not prove; that policy is owned by ADR-004.

## Rejected alternatives

- **"Last write wins" for `current_revision_id`.** Rejected: it cannot distinguish an out-of-order stream from a
  legitimate update, and Blueprint §28 states explicitly that no universal last-write-wins exists.
- **Validating the target stamp when the task is launched and trusting it at commit.** Rejected: cancellation
  and actor teardown are not delivery guarantees (Blueprint §64, §77); revocation or disable/re-enable can land
  between launch and commit, which is exactly what I-12 forbids.
- **Making `AdmissionEngine` an actor (or letting the `AcquisitionCoordinator` own validity).** Rejected:
  correctness would depend on ephemeral memory, and SQLite already provides the serialization boundary; tech
  arch §21 and Blueprint §66 keep authority in SQLite.
- **Durable per-item rejection as the default for page checkpoints.** Rejected as default: advancing past a page
  whose valid items were dropped is precisely the checkpoint-ahead corruption of Blueprint §61; it stays an
  opt-in contract for connectors that can prove resumption safety.
- **Fingerprinting batches with `hashValue`/`Hasher` or with the connector's own opaque fingerprint only.**
  Rejected: `hashValue` is per-process (precedent: `feedmine/Services/FeedDisplayState.swift:427-429`) and an
  opaque connector fingerprint cannot be re-verified after the connector's version changes.
- **Writing the checkpoint in a second, short transaction after the content transaction.** Rejected: it makes
  "checkpoint ahead of committed content" a reachable state, and re-delivery of the batch then becomes
  indistinguishable from progress.

`admission_rejection` (the D7 opt-in contract) is deliberately not specified here: its columns, retention and
quota belong with the durability decision.

**OPEN:** durable representation and reconciliation of leases. This ADR validates `lease_epoch`, an integer
bumped on revocation; whether a lease must additionally survive process death as its own row (owner + expiry)
and how an expired lease is reconciled is **ADR-004**'s to close, because it is a durability/lifecycle question,
not a write-admission one.

**OPEN:** retention of `admission_batch` receipts and of `connector_evidence` — how long a replay must remain
answerable, and the quota that bounds it — **ADR-004**.

**OPEN:** numeric bounds for observation count and bytes per batch. The mechanism (reject oversize, never
advance the checkpoint) is decided here; the numbers are per-purpose budgets, so **ADR-005** must close them.

### Swift (proposed signatures)

struct TargetStamp: Sendable, Equatable {
    let targetID: AcquisitionTargetID
    let targetGeneration: UInt64
    let bindingRevision: UInt64
    let leaseEpoch: UInt64
    let checkpointRevision: UInt64        // expected checkpoint revision (CAS)
}

enum RevisionPrecedence: Sendable, Equatable {
    case makeCurrent(expectedRevision: OriginRevisionID?)
    case historicalOnly
    case duplicate(of: OriginRevisionID?)
}

struct AdmissionBatch: Sendable {
    let batchID: BatchID                  // stable across retries; connector-supplied
    let stamp: TargetStamp
    let fingerprint: BatchFingerprint     // SHA-256 over canonical serialization
    let observations: [TranslatedObservation]
    let nextCheckpoint: ConnectorCheckpoint?
}

struct AdmissionEngine {                  // value type, not an actor (D10)
    func admit(_ batch: AdmissionBatch, in db: Database) throws -> AdmissionResult
}

enum AdmissionResult: Sendable, Equatable {
    case admitted(supplyGeneration: UInt64, checkpointRevision: UInt64, receipt: AdmissionReceipt)
    case replayed(receipt: AdmissionReceipt)
    case duplicate(of: OriginRecordID)
    case staleTarget(expectedGeneration: UInt64, actualGeneration: UInt64)
    case staleCheckpoint(expectedRevision: UInt64, actualRevision: UInt64)
    case batchConflict(batchID: BatchID)
    case identityConflict(externalObjectKey: ExternalObjectKey)
    case invalidObservation(index: Int, reason: InvalidObservationReason)
    case storageFailure(StorageFailure)
}

actor RuntimeWriteCoordinator {           // D11: no critical write type is accepted here
    func enqueue(_ write: NonCriticalWrite)   // .exposure | .telemetry | .sourceHealth | .diagnosticCounter
}

## Invariants

1. No transaction mutates canonical supply, membership, a projection or a checkpoint without a `TargetStamp` that matched the durable target row at commit time. *(I-12)*
2. An admission checkpoint never advances beyond content admitted or durably rejected in the same transaction. *(I-11)*
3. `connector_checkpoint.checkpoint_revision` never decreases and changes only under the CAS predicate `WHERE checkpoint_revision = expected`. *(I-11)*
4. `origin_revision` payload columns are immutable after insert; any such UPDATE aborts the transaction. *(I-06)*
5. `origin_record.current_revision_id` moves only by compare-and-swap against the exact expected revision; a failed CAS leaves it unchanged. *(Blueprint §28; no I-nn)*
6. Re-admitting a batch with the same `batchID` and fingerprint performs zero canonical mutations and does not increment `SupplyGeneration`.
7. A `batchID` re-used with a different fingerprint never mutates canonical state.
8. `SupplyGeneration` increases at most once per transaction and only when selectable supply changed.
9. While a write transaction is open, the executing code performs no suspension, network call, parse, decode or external callback.
10. Only `PublicationCoordinator` inserts into `feed_segment` or `published_card`. *(I-10)*
11. Two concurrent publications cannot commit the same tail: at most one append commits per `(edition_id, segment_ordinal)`, and `(edition_id, absolute_ordinal)` is never duplicated. *(I-07)*
12. A returned `COMMIT` is authoritative: a later process death before notification neither rolls it back nor applies it twice.
13. Stale work leaves no canonical residue; the only permitted residue is content-addressed orphan cache under quota and non-sensitive aggregate counters.
14. Editorial precedence is decided from a connector instruction, never from arrival order, wall clock or payload inspection in the core. *(no I-nn; plan §7)*

## Edge cases

- Crash between any two steps above: covered by the per-step table; the property that matters is that no step writes a checkpoint or a generation ahead of the content it belongs to.
- Crash after `COMMIT`, before notification: the commit stands; a resend returns `replayed`, and a session that never received the event still observes the new supply because selection reads durable state.
- Duplicate delivery of one event twice in the same process, or a replay after a lost response: identical `batchID` + fingerprint ⇒ `replayed` with no mutation; a diverging body under the same ID ⇒ `batchConflict` with no mutation; no in-memory dedup is trusted.
- Connector resets its cursor to a lower value: the CAS fails (`staleCheckpoint`); the runtime never rewinds a checkpoint implicitly, because rewinding is a new target/binding decision, not an admission side effect.
- A→B→A across contexts/epochs: the epoch in the stamp makes the late A batch stale even though its content is not, and A's checkpoint is not rolled back.
- Disable/re-enable of a binding or target: the epoch bump makes results produced under the old epoch stale; re-enable does not resurrect them.
- Revoke, then a late stream event: rejected by D1 before any mutation (I-12), even though the task was already cancelled.
- Clock skew: `observedAt` is always the runtime's own observation time and is the only timestamp the core trusts; a future or implausible `authoredAt` is a normalised claim, never a reason to overwrite current (Blueprint §35).
- Version collision: the same `externalVersionKey` with a divergent payload is an audited `identityConflict`, never an overwrite (ADR-003 owns the conflict record).
- One invalid observation in a page, or an oversized batch: `invalidBatch` with no checkpoint advance; the connector must fix, split or use the opt-in per-item contract.
- Cancellation arriving mid-transaction: the transaction completes or rolls back as a unit; `Task.isCancelled` is checked before starting and after committing, never relied on for correctness.
- `SQLITE_BUSY` or disk full during steps 5–10: rollback and `storageFailure`, checkpoint unchanged, stamp re-read before any retry; the user-visible recovery path is ADR-004's.
- Migration: a database opened at the previous schema must migrate deterministically or be rejected explicitly; an in-flight stamp from the old schema is not reinterpreted under the new one.
- Catalog replacement (`feedmine/FeedEngine/SQLiteCatalogStore.swift:65-76`) while a write transaction is open: no step reads the catalog, so a swapped catalog file cannot enter canonical state.
- User action (bookmark) committed while admission retries: the two databases share no commit, so the action is applied to `user.sqlite` first and projected with a watermark (ADR-004, plan §5.2); admission never infers user intent from its own failure.
